# CLAUDE.md

Головний файл-навігатор. Читається першим у кожній сесії.
Документація — українською. Код, шляхи, назви таблиць/полів/компонентів — англійською.

**Одиниця роботи — модуль = одна сторінка/екран.**
Проєкт не описується наперед. Він нарощується задача за задачею, і кожна задача лишає слід у доках.
**Система мультитенантна.** Розділ 6 — не рекомендації, а тверді правила.

---

## 0. Економія контексту

Читається **завжди**: `CLAUDE.md`, `docs/map.md`, `docs/roadmap.md`.
Усе інше — за таблицею в розділі 4. Ніколи не читай усі модулі підряд.

Обмеження: `map.md` — один рядок на модуль. Файл модуля ≤ 120 рядків (перевищив стабільно — розріж на піддокумент, `docs/_module-template.md` розділ «Коли модуль переріс ліміт»). У доках — факти, шляхи, статуси; код не переказувати. У секції «Зроблено» лишати останні 10 записів. `roadmap.md` — виконані (`[x]`) пункти, що вийшли за останні ~10 позицій «Беклогу», переносити в `decisions.md`/файл модуля і прибирати з roadmap.md — він читається щосесії, не повинен рости без стелі.

## 3. Робочий цикл задачі

**Крок 1 — старт.** Прочитай `CLAUDE.md`, `map.md`, `roadmap.md`. Визнач модуль.
- Модуль є в `map.md` → прочитай `docs/modules/<name>.md` і доповідай у 3 рядки перед кодом:
  ```
  Модуль products: UI [готово] · Логіка [в роботі] · Бек [—]
  Файли: src/pages/Products.jsx, src/components/ProductCard.jsx
  Відкрито: пагінація, empty state
  ```
- Модуля немає → створи запис у `map.md` і файл модуля за шаблоном (розділ 5).

Задача з візуалом → прочитай також `design.md` і `ui-kit.md`.
Бракує даних — **питай, не вигадуй.**

**Крок 2 — реалізація.** Тільки те, про що просили. Ніяких «заодно».

**Крок 3 — фіксація одразу після реалізації** (не чекаючи підтвердження):
файл модуля (файли, залежності, статус `в роботі`, запис у «Зроблено») · `map.md` · `roadmap.md` · `ui-kit.md` / `db.md` / `api.md`, якщо торкався · `decisions.md`, якщо рішення нетривіальне.

**Крок 4 — підтвердження.** Коли людина каже **«мене все влаштовує»** або еквівалент:
статус шару → `готово`, пункт роадмапу → `[x]`, коміт `feat(<модуль>): <що зроблено>`.

**Крок 5 — перемикання.** **Не переходь на інший модуль, поки поточний не зафіксовано.** Це головна причина каші. «Переходимо на X» → спершу доведи крок 3–4 до кінця.

## 4. Що читати під яку задачу

| Задача | Читати |
|---|---|
| нова сторінка/екран | `map.md`, `design.md`, `ui-kit.md`, найближчий модуль як зразок |
| правка сторінки | `docs/modules/<name>.md` → далі **тільки перелічені там файли**. Секції файлу модуля йдуть у фіксованому порядку (шаблон — `docs/_module-template.md`): Файли → Дані → Доступ → Зв'язки → Зроблено → Відкрито. Типова правка не потребує історії «Зроблено» — читай Файли+Відкрито вибірково (`offset`/`limit`), «Зроблено» — лише під «чому так зроблено» чи перед дописуванням нового запису |
| спільний компонент | `ui-kit.md`, `design.md` |
| БД / міграція | `conventions.md` + лише розділ конкретної таблиці в `db.md` (`### <table>`, шукай через grep) — весь файл лише коли треба огляд усієї схеми |
| ендпоінт, бекенд | `api.md`, `conventions.md`, файл модуля |
| авторизація, ролі, доступ | `stack.md`, `conventions.md`, розділ 6 нижче |
| «чому так зроблено» | `decisions.md` |
| деплой | `env.md` |

## 6. Мультитенантність — тверді правила

Порушення будь-якого з цих пунктів = витік даних між клієнтами. Це найдорожча помилка в проєкті.

1. **Кожна прикладна таблиця має колонку `tenant_id`.** Виняток — тільки глобальні довідники, і кожен такий виняток записується в `db.md` з поясненням.
2. **Жоден запит на читання чи запис не виконується без фільтра `tenant_id`.** `WHERE id = ?` без tenant_id — заборонено завжди, навіть якщо «id унікальний».
3. **`tenant_id` береться тільки з серверної сесії/токена.** Ніколи з URL, форми, заголовка чи будь-чого, що прислав клієнт.
4. **Композитні індекси починаються з `tenant_id`:** `(tenant_id, created_at)`, `(tenant_id, status)`.
5. **Кожен UNIQUE — у межах тенанта:** `UNIQUE (tenant_id, email)`, а не `UNIQUE (email)`.
6. **Доступ до даних — через один шар.** Ніяких прямих запитів у контролерах чи шаблонах. Шар сам підставляє `tenant_id`, щоб забути було неможливо.
7. **Перед будь-якою дією над записом — перевір належність до тенанта**, навіть якщо id прийшов з попереднього запиту.
8. **Суперадмін** (якщо є) працює окремим явним шляхом із логуванням. Ніяких «якщо роль admin — не фільтрувати».

При будь-якій роботі з БД проговори в звіті, як саме дотримано пунктів 2 і 3.

## 7. БД і безпека

Деталі — в `docs/conventions.md`, він створюється на старті. Базове:

**Швидкодія.** Індекс під кожен частий `WHERE`, `JOIN`, `ORDER BY`. Для нового нетривіального запиту — `EXPLAIN`, результат коротко в звіті. Ніяких N+1: запит у циклі — це помилка. На списках завжди `LIMIT` і пагінація. Індекси фіксуються в `db.md` разом із таблицею.

**Безпека.** Тільки параметризовані запити — конкатенація SQL заборонена в будь-якому вигляді. Валідація на сервері незалежно від того, що робить фронт. Екранування на виводі. Паролі — сучасний хеш (для PHP `password_hash`), ніколи md5/sha1. CSRF-токен на формах, обмеження спроб входу. Тексти помилок користувачу — загальні, деталі в лог. Секрети — тільки в `.env`, ніколи в коді, доках чи комітах. Файли, завантажені користувачем, — перевірка типу й розміру, зберігання поза webroot.

## 8. Git

Коміт після кожної підтвердженої задачі. Формат: `feat(products): сітка товарів`, `fix(login): валідація email`, `docs: оновлено map`. Код і доки — в одному коміті. Ризикована зміна (рефакторинг, міграція, зміна схеми) — окрема гілка. Ніякого `--force`, переписування історії й видалення гілок без прямої вказівки. Перед великою зміною скажи, до якого коміту можна відкотитись.

## 9. Правила проти каші

1. Перед створенням компонента — перевір `ui-kit.md`. Схоже вже є — використай або розшир.
2. Компонент використали двічі — переносимо в ui-kit і фіксуємо в `ui-kit.md`.
3. Перед створенням модуля — перевір `map.md`.
4. Один модуль — один файл доки. Виняток — модуль переріс ліміт розділу 0: тоді піддокумент за правилом `docs/_module-template.md`, не окремий модуль.
5. Візуал робимо за `design.md`. Відступ від еталона — тільки з питанням, не мовчки.
6. Файл коду переріс ~400 рядків — ріж і онови файл модуля.
7. Не міняй те, що працює, без запиту.
8. Не вигадуй назви полів, ендпоінтів, API.
9. Не додавай залежність без погодження.
10. Доки розійшлися з кодом — скажи вголос.

## 10. Звірка

За командою **«звірка»** (і самостійно, якщо помітив розбіжність):
пройди по `map.md` і модулях; перевір, що всі перелічені файли існують і що нема файлів коду, не згаданих у жодному модулі; перевір статуси; перевір, що всі таблиці в `db.md` мають `tenant_id` та індекси.
Виведи список розбіжностей **і чекай рішення.** Нічого не виправляй самовільно.
