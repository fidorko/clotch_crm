# Conventions

## Іменування
- Код, шляхи, назви таблиць/полів/компонентів — англійською.
- Таблиці БД: `snake_case`, множина (`products`, `product_skus`).
- Поля БД: `snake_case`.
- TypeScript: `camelCase` для змінних/функцій, `PascalCase` для компонентів і типів.
- Файли компонентів: `PascalCase.tsx` (`ProductCard.tsx`).
- Роути Next.js: `kebab-case` де можливо.

## Мультитенантність (виконання розділу 6 CLAUDE.md)
- Кожна прикладна таблиця → колонка `tenant_id uuid not null`, `FK → tenants.id`.
- Увесь доступ до даних — через єдиний data-access шар (`src/server/data/*`), який приймає `tenantId` як обов'язковий параметр (типізація не дає викликати без нього).
- `tenantId` дістається тільки з серверної сесії (`getSession()`), ніколи з `params`, `searchParams`, body чи заголовків.
- Composite-індекси починаються з `tenant_id`: `(tenant_id, created_at)`, `(tenant_id, status)`.
- UNIQUE — завжди в межах тенанта: `UNIQUE (tenant_id, email)`.
- PostgreSQL Row-Level Security — увімкнено на кожній тенантній таблиці як другий рубіж (політика звіряє `tenant_id` з `current_setting('app.tenant_id')`, яку виставляє сервер на початку транзакції).
- Суперадмін-шлях: окремі функції з префіксом `superadmin*`, обов'язковий запис у лог-таблицю `audit_log` при кожному використанні.

## БД
- Тільки параметризовані запити (Drizzle query builder), жодної конкатенації SQL.
- Індекс під кожен частий `WHERE`, `JOIN`, `ORDER BY` — фіксується в `db.md` разом із таблицею.
- Для нетривіального запиту — `EXPLAIN`, коротко в звіті.
- Списки — завжди `LIMIT` + пагінація, без N+1 у циклі.
- Міграції — через Drizzle Kit, окрема гілка на ризиковану зміну схеми.

## Безпека
- Паролі — `bcrypt`/`argon2` (не md5/sha1).
- Валідація вхідних даних на сервері (Zod) незалежно від фронта.
- Екранування на виводі (React робить це за замовчуванням — не обходити через `dangerouslySetInnerHTML` без потреби).
- CSRF-захист на формах, rate-limit на спроби входу.
- Тексти помилок користувачу — загальні («Щось пішло не так»), деталі — в серверний лог.
- Секрети — тільки в `.env`, ніколи в коді/доках/комітах.
- Файли від користувача — перевірка типу й розміру, зберігання поза webroot (наприклад, S3-сумісне сховище або volume поза `public/`).

## Стиль коду
- TypeScript strict mode.
- Компонент з ui-kit — перевірити `ui-kit.md` перед створенням нового.
- Файл коду > ~400 рядків — різати, оновити файл модуля.
- Без коментарів «що робить код» — тільки коли неочевидне «чому».

## Мітки компонентів у dev-режимі
- Поки UI модуля має статус «в роботі», кожен блок/секція сторінки (не дрібні атоми з ui-kit — Button, Input тощо) обгортається `DevBlockLabel` (`src/components/dev/DevBlockLabel.tsx`): жовта мітка з назвою компонента у верхньому лівому куті + пунктирна рамка блоку.
- Прапорець показу — по одному на модуль, у `src/lib/dev/dev-flags.ts` (`DEV_BLOCK_LABELS.<module>`).
- Коли статус UI модуля переходить у «готово» (крок 4 CLAUDE.md) — прапорець модуля вимикається (`false`) у тому самому коміті, що й зміна статусу.
- Референс до конкретного блоку в розмові — за назвою з мітки (вона ж назва компонента-файлу).

## SEO
- CRM-екрани (усе за авторизацією, мультитенантні дані) — `noindex, nofollow` за замовчуванням. Ставиться один раз через `metadata` у layout розділу (див. `src/app/products/layout.tsx`), не сторінка за сторінкою.
- Публічні сторінки (лендинг, маркетинг — заплановано) — повне SEO: `title`/`description` через `generateMetadata`, OG-теги, дозволяючий запис у `src/app/robots.ts`, за потреби `sitemap.ts`.
- `src/app/robots.ts` — динамічний robots.txt (Next.js App Router). Зараз `disallow: "/"` для всього сайту — публічного контенту ще нема. Оновити, коли з'явиться лендинг.
- Кожна сторінка має власний `title` через `generateMetadata`/`metadata`, навіть у CRM — впливає на заголовок вкладки браузера, не лише на пошук.
