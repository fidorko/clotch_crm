# Модуль: products

**Статус:** UI `в роботі` · Логіка `—` · Бек `в роботі` · БД `в роботі`
**Маршрут:** /products, /products/[id]
**Оновлено:** 2026-08-03 (нова вкладка «Технічні дані» + журнал подій товару — див. `products-technical-tab.md`)

## Призначення
Список товарів (пошук/фільтри/пагінація/видалення, за мотивами референсного скріншоту, у власному стилі) і картка товару: загальна інформація, фото, варіанти SKU (колір × розмір), залишки, статистика по товару. За зразком `Image.png`.

## Дані
Сторінка `/products` (список) читає `listProducts(tenantId, filters)` — фільтри/пагінація йдуть через `searchParams` URL (`q`/`category`/`status`/`stock`/`page`), сторінка серверна, `ProductsTable` — клієнтський контролер фільтрів, що навігує на нову URL (`router.push`). «Додати товар» створює рядок у `products` мінімальними NOT NULL-плейсхолдерами й `is_draft = true`, одразу веде на `/products/[id]`.
На картці товару вся форма (ім'я/статус/категорія/постачальник/бренд/колекція/характеристики/ціни/метадані/теги) тепер зберігається одним запитом через `saveProductAction` → `saveProduct` (`server/data/products.ts`) — оновлює рядок `products` і синхронізує `product_tags` (знайти-або-створити тег за міткою, tenant-скоуповано, повна заміна набору тегів товару), знімає `is_draft`. `product.season` — і далі read-only (у формі нема поля для редагування, як і раніше); `brand` і `supplierId` тепер редаговані (обидва — `ProductInfoPanel`).
Сторінка `/products/[id]` читає реальні дані з PostgreSQL через `getProductById(tenantId, id)` (`src/server/data/products.ts`) — таблиці `products`, `product_skus`, `product_photos`, `product_size_measurements`, `product_tags`+`custom_characteristic_values` (теги — характеристика `system_key="tags"`, не окрема таблиця, `db.md`). `tenantId` поки з dev-константи (`TODO(auth)`, `db.md`). Мок `src/lib/mocks/products.ts` лишається як джерело сіду (`npm run db:seed`), UI-код на нього більше не посилається (крім `selectedSku` — див. «Відкрито»).
`page.tsx` також тягне `listCategories(tenantId)` (`server/data/categories.ts`, той самий шар, що й у `settings`) і пробрасовує в `ProductGeneralTab` → `ProductInfoPanel` для ієрархічного піклера категорії.
Розмірна сітка (`ProductSizeChart.tsx`, 2026-08-02) — реальна редагована сітка «розмір × точка заміру», за прямою вказівкою людини: рядки з `product_skus.size`, колонки з категорійно закріплених `measurement_types`/`measurement_values`, значення — нова таблиця `product_size_measurements` (`db.md`), «довідка» (`MeasurementGuide.tsx`) — схематичні ілюстрації замінили колишню картку `ProductMeasurements`. Кольори SKU-матриці й поля «Колір» — вже з БД (`server/data/colors.ts`, `listColors(tenantId)` у `page.tsx`, settings → «Довідники» → «Кольори»), `product_skus.color`/`color_hex` лишаються копією значення на момент створення SKU (не FK).

**Фото й SKU-матриця тепер реально в БД, поза "Створити товар"/"Редагувати".** Фото товару (`ProductPhotoGallery`) і фото кольору (`ProductSkuTable`, під назвою кожного кольору) зберігаються одразу при завантаженні (Server Action пише файл на диск + рядок у `product_photos`/`product_color_photos`), без очікування кнопки збереження форми — так само, як зображення категорій. Фото кольору навмисно **не** прив'язане до конкретного SKU — на колір завжди припадає кілька SKU (по розміру), і фото те саме для всіх; прив'язка лише до `product_id` + вільний текст `color` (не FK), тому фото можна завантажити навіть до першого доданого розміру цього кольору. SKU-матриця (`ProductSkuSection`) при відкритті сторінки відновлює `colors`/`sizes`/`skus` із `product.skus` (реальні дані з БД), а фото кольорів — із `product.colorPhotos`; кожна дія (додати/видалити SKU, видалити колір/розмір цілком, автогенерація) одразу пише в `product_skus` через Server Action — колір/розмір як такі лишаються не персистентними окремо (не таблиця, `db.md`), лише похідні від наявних SKU.
