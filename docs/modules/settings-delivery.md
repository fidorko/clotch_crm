# Модуль: settings — піддокумент «Доставка»

Частина модуля `settings` (`docs/modules/settings.md`) — винесено окремо за тим самим правилом, що «Склади»/«Довідники» (`CLAUDE.md`, розділ 0). Статус/доступ/зв'язки — спільні з `settings.md`, тут немає власного запису в `map.md`.

**Маршрут:** /settings?tab=delivery

## Призначення
Розділ «Доставка» (сайдбар → Налаштування → Доставка) — плоский список способів доставки тенанта: вмикач (Switch), назва, статус-бейдж, колонка «Юридичні особи», олівець (редагування), кошик (видалення, з підтвердженням), «+ Додати спосіб доставки».

**2026-08-06, сьомий прохід — розділення на список і конфігурацію по юридичній особі** (пряма вказівка людини: «способи доставки то одні на тенанта, а от налаштування різні» — у кожного ФОП/ТОВ власний кабінет перевізника, ключ, відправник, реквізити). Таблиця `delivery_methods` лишилась лише списком (назва/`carrier_key`/увімкнено/позиція, **одна на тенанта**), уся конфігурація нижче (Дані API, Відправник, Хто платить тощо) переїхала в нову `delivery_method_entity_settings` — по одному рядку на пару (спосіб доставки, юридична особа, `docs/modules/settings-general.md`). У попапі редагування — перемикач «Юридична особа» (`Select`), **автообраний і прихований, якщо ФОП/ТОВ лише один**; з'являється щойно їх стає два й більше. Новостворений ФОП/ТОВ одразу отримує порожній рядок конфігурації на кожен наявний спосіб доставки (`seedDeliveryMethodEntitySettingsForLegalEntity`, викликається в тій самій транзакції, що створення юридичної особи — `company-legal-entities.ts`). У списку — нова колонка «Юридичні особи»: для кожного ФОП/ТОВ окремо «Налаштовано»/«Потребує налаштування» (є `api_key` чи ні); статус-бейдж («Активний»/«Не активний») тепер означає лише `is_enabled` способу в цілому, не наявність ключа.

**2026-08-05, другий прохід (пряма вказівка людини) — попап редагування розширено налаштуваннями перевізника.** Людина явно зазначила: «не всі вони є в API, але саме вони потрібні користувачу CRM» — тобто частина полів (відправник, пакування, друк) це CRM-конфігурація для довідки/майбутньої інтеграції, не пряме дзеркало методів Нової пошти. Показуються лише коли `requiresApiKey=true` (Самовивіз — стара коротка форма: назва+увімкнено). Секції попапу:
- **Дані API** — назва (**лише для читання для 4 системних способів** — `pickup`/`nova_poshta`/`ukrposhta`/`meest_express`, `SYSTEM_CARRIER_KEYS`, сьомий прохід: «Нова пошта тут не редагується, це системний спосіб доставки» — редагована лише для довільних, доданих тенантом), поле ключа + **«Перевірити підключення»** (реальний виклик `Address.getCities`, лише для `carrierKey==="nova_poshta"` — інші перевізники чесно повертають «не реалізовано», без вдавання). Чекбокс «Потребує API-ключ перевізника» (шостий прохід) і **«Увімкнено» (сьомий прохід)** — обидва прибрано з UI: `requiresApiKey` виставляється автоматично при створенні; вмикання/вимикання способу доставки відбувається **лише зі списку** (`DeliveryTab.tsx`, колонка «Увімкнено»), не з попапу редагування.
- **Відправник за замовчуванням** — для Нової пошти (`carrierKey==="nova_poshta"`) **реальні дані з облікового запису тенанта**: контрагент — `Select` з `Counterparty.getCounterparties(Sender)`; контактна особа — каскадний `Select` з `Counterparty.getCounterpartyContactPersons` (телефон підставляється разом, не редагується окремо). **«Звідки відправляємо» (шостий прохід, замінює колишнє «Тип доставки можливий»)** — radio **Відділення / Адреса**, обирається один раз: «Відділення» → місто+відділення (`Address.getCities`/`getWarehouses`, як і раніше); «Адреса» → місто+вулиця (`Address.getStreet` — **однина!**, `getStreets` не існує в API, перевірено живим викликом) + будинок (вільний текст, немає довідника будинків). Для решти перевізників (без реальної інтеграції) — вільний текст, як і раніше.
- **Хто платить** — radio, підписи з `NOVA_POSHTA_PAYER_TYPES` (Sender/Recipient/ThirdPerson, перевірено живим викликом `getTypesOfPayers`). За замовчуванням отримувач.
- **Контроль оголошеної вартості** — radio («завжди сума замовлення» / «мінімальна сума» + `DecimalInput`, за замовчуванням 500 грн).
- **Опис відправлення** — що підставляти в поле «Опис вантажу» ЕН: radio (ID замовлення / **SKU** — перейменовано з «Артикул товару», шостий прохід / назви товарів, за замовчуванням «Назви товарів») + чекбокс «Вказувати кількість».
- **Автоматичні дії** — частота синхронізації (хв), «Оформлювати повернення через API при відмові отримувача на відділенні» (`orderReturnOnRefusal`, вимикач — не автоматика, лише дозвіл дії), repeatable-список «При статусі перевізника X → змінити статус замовлення на Y» — **лівий Select тепер реальні статуси `NOVA_POSHTA_TRACKING_STATUSES`** (шостий прохід, замінює вільний текст; статуси зведено зі сторонньої технічної статті — офіційний список кодів заблокований для бота, `lib/constants/nova-poshta.ts`).
- **Пакування (шостий прохід, спрощено)** — лише вимикач «Використовувати пакування Нової пошти»; конкретну позицію (раніше — Combobox над `getPackList` прямо тут) тепер обирають пізніше, при оформленні замовлення, не в налаштуваннях.
- **Маркування (шостий прохід, замінює «Друк»)** — radio **Термопринтер** (101×101мм, рулон на 500, напр. Zebra GC420d) / **Звичайний принтер** (A4, 6 етикеток по 105×99мм на аркуш), з розмірами й поясненням прямо у варіантах вибору (`docs/carriers/novaposhta/printing.md` — дослідив офіційні джерела НП: сторінку товару з реальним самоклейким папером, сторінку принтера маркування). Поле «Принтер» (назва пристрою) — **прибрано за прямою вказівкою людини**.

**Усе перелічене — лише конфігурація/зберігання**, окрім «Перевірити підключення» й самих живих довідникових пошуків (місто/відділення/вулиця/контрагент — реальні виклики, підтверджені живою перевіркою нижче): жодна фонова синхронізація, авто-повернення чи застосування правила статусу не виконується — логіки, що читає ці поля й щось із ними робить (створення ЕН, реальне замовлення повернення), ще нема.

**Статус — обчислюється, не зберігається:** «Не активний» (вимкнено), «Потрібен ключ» (увімкнено + потребує ключ + ключа нема), «Активний» (увімкнено і ключ є або не потрібен) — `statusOf()` у `DeliveryTab.tsx`.

**Ключ Нової пошти (2026-08-05) — людина дала реальний тимчасовий ключ у чаті** для налаштування інтеграції. Записаний лише в `.env` (`NP_API_KEY`, людина сама дописала рядок — пісочниця блокує запис/читання `.env` навіть з дозволу користувача). Дев-сід підставляє його в рядок «Нова Пошта» (`seed-delivery-methods.ts`), лише коли `api_key` там ще `NULL` (повторний сід не затре ключ, уведений вручну через UI). Підтверджено живим викликом `Address.getCities` до `api.novaposhta.ua/v2.0/json/` — ключ робочий.

**Референс API перевізника (не залежність):** https://github.com/shopanaio/carrier-api (TS-клієнт + дзеркало офіційної документації НП у `docs/novaposhta-2.0`) використано лише як довідник для пошуку методів/полів офіційного API — код пишеться самостійно проти `api.novaposhta.ua` напряму, без npm-залежності від цього репозиторію (пряма вказівка людини).

**2026-08-05, четвертий прохід — «Дані відправника повинні тягнутися з АПІ з мого ключа»** (пряма вказівка людини): усі значення в цьому попапі, де реально є довідник у НП API, перевірено живим викликом (не вигадано) і підключено як реальний Select/Combobox замість вільного тексту. Стабільні фіксовані словники (типи доставки, платники) — захардкоджено з коментарем-джерелом (`lib/constants/nova-poshta.ts`), не живий запит при кожному відкритті попапу (той самий підхід, що `REFERENCE_ITEM_KINDS`); великі/тенант-специфічні дані (міста, відділення, контрагенти, пакування) — живі виклики.

**2026-08-06, шостий прохід — дизайн попапу.** Ширше вікно (`sm:max-w-2xl` → `sm:max-w-4xl`), 2-колонковий грід логічних карток (`FormSection` — рамка+фон, замінює плоский список секцій одна під одною), лого перевізника в заголовку попапу й поруч з назвою в списку (`CARRIER_LOGOS`, `public/carriers/*` — 4 файли, надані людиною, перенесені з кореня репозиторію в правильну Next.js-конвенцію), іконки `lucide-react` у заголовку кожної картки.

**2026-08-06, сьомий прохід — уточнення розкладки й прав редагування** (пряма вказівка людини: «Автоматичні дії там не вміщаються назви статусів»): вікно розширено ще раз (`sm:max-w-4xl` → `sm:max-w-6xl`). Розкладка тепер: «Відправник за замовчуванням» — повношириний блок; «Хто платить»+«Контроль вартості» та «Пакування»+«Маркування» — пара 2 колонки; «Опис відправлення» і «Автоматичні дії» — повноширині блоки (довгі назви статусів перевізника й обидва Select у правилі більше не тиснуться). `DeliveryMethodShippingRulesFields.tsx` розділено на два експортовані компоненти (`DeliveryMethodPayerFields`/`DeliveryMethodDescriptionFields`), щоб попап міг розкласти їх окремо. Назва системних способів доставки (4 стартові) — `disabled` Input, не редагується (`SYSTEM_CARRIER_KEYS`, `lib/constants/carrier-logos.ts`); довільні способи, додані тенантом, лишаються редаговані. «Увімкнено» — прибрано з попапу повністю, перемикається тільки з рядка списку.

**2026-08-06, п'ятий прохід — модуль перевізників-абстракція.** Пряма вказівка людини: повністю автономний `src/server/carriers/` (interface+factory+provider на кожен перевізник) — CRM більше не викликає жоден метод Нової пошти напряму, лише універсальний `CarrierProvider`.
