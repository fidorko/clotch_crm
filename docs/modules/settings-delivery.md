# Модуль: settings — піддокумент «Доставка»

Частина модуля `settings` (`docs/modules/settings.md`) — винесено окремо за тим самим правилом, що «Склади»/«Довідники» (`CLAUDE.md`, розділ 0). Статус/доступ/зв'язки — спільні з `settings.md`, тут немає власного запису в `map.md`.

**Маршрут:** /settings?tab=delivery

## Призначення
Розділ «Доставка» (сайдбар → Налаштування → Доставка) — плоский список способів доставки тенанта: вмикач (Switch), назва, статус-бейдж, олівець (редагування), кошик (видалення, з підтвердженням), «+ Додати спосіб доставки».

**2026-08-05, другий прохід (пряма вказівка людини) — попап редагування розширено налаштуваннями перевізника.** Людина явно зазначила: «не всі вони є в API, але саме вони потрібні користувачу CRM» — тобто частина полів (відправник, пакування, друк) це CRM-конфігурація для довідки/майбутньої інтеграції, не пряме дзеркало методів Нової пошти. Показуються лише коли `requiresApiKey=true` (Самовивіз — стара коротка форма: назва+увімкнено). Секції попапу:
- **Дані API** — назва, чекбокс «Потребує API-ключ», поле ключа + **«Перевірити підключення»** (реальний виклик `Address.getCities`, лише для `carrierKey==="nova_poshta"` — інші перевізники чесно повертають «не реалізовано», без вдавання), «Увімкнено».
- **Відправник за замовчуванням** — для Нової пошти (`carrierKey==="nova_poshta"`) **реальні дані з облікового запису тенанта** (2026-08-05, четвертий прохід, пряма вказівка людини): контрагент — `Select` з `Counterparty.getCounterparties(Sender)`; контактна особа — каскадний `Select` з `Counterparty.getCounterpartyContactPersons` (обраної контрагента), телефон підставляється разом (не редагується окремо); місто/відділення — живий пошуковий `Combobox` (`Address.getCities`/`Address.getWarehouses`, debounce 300мс, обране показується рядком «Обрано: …» під полем — Base UI Combobox скидає текст інпуту, коли `value` лишається транзитним `null`, той самий патерн, що `AddSkuCombobox`). Для решти перевізників (без реальної інтеграції) — вільний текст, як і раніше.
- **Тип доставки можливий** — реальні 5 комбінацій `CommonGeneral.getServiceTypes` (Відділення—Відділення/Відділення—Адреса/Адреса—Відділення/Адреса—Адреса/Адреса—Поштомат, `lib/constants/nova-poshta.ts`), масив `text[]` замість колишніх 3 вигаданих булевих, за замовчуванням усі 5.
- **Хто платить** — radio, підписи з `NOVA_POSHTA_PAYER_TYPES` (Sender/Recipient/ThirdPerson, перевірено живим викликом `getTypesOfPayers`) — хедж «якщо підтримується» прибрано, підтримку підтверджено. За замовчуванням отримувач.
- **Контроль оголошеної вартості** — radio («завжди сума замовлення» / «мінімальна сума» + `DecimalInput`, за замовчуванням 500 грн).
- **Опис відправлення** — що підставляти в поле «Опис вантажу» ЕН: radio (ID замовлення / артикул товару / назви товарів, за замовчуванням «Назви товарів») + чекбокс «Вказувати кількість» (за замовчуванням увімкнено).
- **Автоматичні дії** — частота синхронізації (хв), «Оформлювати повернення через API при відмові отримувача на відділенні» (вимикач, перейменовано з «автоматичне» — людина уточнила: автоматики нема, але замовити повернення по API можна, `orderReturnOnRefusal`), repeatable-список «При статусі перевізника X → змінити статус замовлення на Y».
- **Пакування** — radio (не використовувати/пакування перевізника/власне); для Нової пошти обрання середнього варіанту відкриває живий фільтрований `Combobox` над реальним `CommonGeneral.getPackList` (десятки позицій, отримано одним запитом, фільтрація клієнтська — той самий підхід, що `AddSkuCombobox`).
- **Друк** — формат етикетки, формат ЕН, принтер (вільний текст — реального вибору фізичного принтера з браузера нема, лише мітка для довідки).

**Усе перелічене — лише конфігурація/зберігання**, окрім «Перевірити підключення» й самих живих довідникових пошуків (місто/відділення/контрагент/пакування — реальні виклики, підтверджені живою перевіркою нижче): жодна фонова синхронізація, авто-повернення чи застосування правила статусу не виконується — логіки, що читає ці поля й щось із ними робить (створення ЕН, реальне замовлення повернення), ще нема.

**Статус — обчислюється, не зберігається:** «Не активний» (вимкнено), «Потрібен ключ» (увімкнено + потребує ключ + ключа нема), «Активний» (увімкнено і ключ є або не потрібен) — `statusOf()` у `DeliveryTab.tsx`.

**Ключ Нової пошти (2026-08-05) — людина дала реальний тимчасовий ключ у чаті** для налаштування інтеграції. Записаний лише в `.env` (`NP_API_KEY`, людина сама дописала рядок — пісочниця блокує запис/читання `.env` навіть з дозволу користувача). Дев-сід підставляє його в рядок «Нова Пошта» (`seed-delivery-methods.ts`), лише коли `api_key` там ще `NULL` (повторний сід не затре ключ, уведений вручну через UI). Підтверджено живим викликом `Address.getCities` до `api.novaposhta.ua/v2.0/json/` — ключ робочий.

**Референс API перевізника (не залежність):** https://github.com/shopanaio/carrier-api (TS-клієнт + дзеркало офіційної документації НП у `docs/novaposhta-2.0`) використано лише як довідник для пошуку методів/полів офіційного API — код пишеться самостійно проти `api.novaposhta.ua` напряму, без npm-залежності від цього репозиторію (пряма вказівка людини).

**2026-08-05, четвертий прохід — «Дані відправника повинні тягнутися з АПІ з мого ключа»** (пряма вказівка людини): усі значення в цьому попапі, де реально є довідник у НП API, перевірено живим викликом (не вигадано) і підключено як реальний Select/Combobox замість вільного тексту — `src/server/integrations/nova-poshta.ts` (тонкий клієнт: `searchNovaPoshtaCities`/`searchNovaPoshtaWarehouses`/`listNovaPoshtaSenderCounterparties`/`listNovaPoshtaContactPersons`/`listNovaPoshtaPackList`) + `src/app/settings/delivery/np-lookup-actions.ts` (Server Actions з уведеним, не обов'язково збереженим ключем — той самий підхід, що `testDeliveryApiKeyAction`). Стабільні фіксовані словники (типи доставки, платники) — захардкоджено з коментарем-джерелом (`lib/constants/nova-poshta.ts`), не живий запит при кожному відкритті попапу (той самий підхід, що `REFERENCE_ITEM_KINDS`); великі/тенант-специфічні дані (міста, відділення, контрагенти, пакування) — живі виклики.

- 2026-08-05, четвертий прохід (пряма вказівка людини — «дані відправника мають тягнутися з АПІ», «довідник міст/відділень теж підтягнути», «всі дані у формі перевір по документації, які там варіанти»): дослідив живими викликами реального API з ключем тенанта — `Counterparty.getCounterparties`/`getCounterpartyContactPersons` (реальний контрагент+контактна особа на акаунті), `Address.getCities`/`getWarehouses` (міста/відділення), `CommonGeneral.getServiceTypes`/`getTypesOfPayers`/`getPackList` (тип доставки/платник/пакування — виявив, що модель `Reference` не існує, правильна — `CommonGeneral`). Схема: додано `*Ref`-колонки (контрагент/контактна особа/місто/відділення/пакування) поруч із кешованим описом, `allowedServiceTypes` (`text[]`, реальні 5 Ref замість вигаданих 3 булевих), `orderReturnOnRefusal` (перейменовано з `autoReturnOnRefusal` — JS-назва, без міграції колонки, людина уточнила: автоматики нема, лише можливість замовити повернення по API). - [ ] Реальне створення ЕН/ТТН (`InternetDocument.save`), трекінг, реальне замовлення повернення — не реалізовано; є лише «Перевірити підключення» й живі довідникові пошуки (міста/відділення/контрагенти/пакування), і лише для Нової пошти — Укрпошта/Meest Express завжди повертають «не реалізовано»

- [ ] «Опис відправлення» (ID замовлення/артикул/назви товарів + кількість) — лише вибір формату в конфігурації; реального збору опису при створенні ЕН нема (створення ЕН взагалі не реалізовано)
