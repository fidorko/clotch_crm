# Модуль: products — піддокумент «Динамічні характеристики картки товару»

Частина модуля `products` (`docs/modules/products.md`) — винесено окремо, бо основний файл модуля вже на межі ліміту (`CLAUDE.md`, розділ 0; правило — `docs/_module-template.md`). Статус/доступ/зв'язки — спільні з `products.md`, тут немає власного запису в `map.md`.

**Маршрут:** /products/[id] (вкладка «Основне»)

## Призначення
Наступний крок після «Закріплення характеристик» на категорії (`settings-category-characteristics.md`): картка товару тепер показує **лише ті характеристики, які закріплені за обраною категорією товару**, замість повністю хардкодних списків (Бренд/Колекція/Сезон/Посадка/Виробник/Тип тканини/Матеріал/Інструкція по догляду — раніше жодне з цих полів не було пов'язане з довідниками, навіть тими, що вже в БД). Категорія стає обов'язковою для нового товару — без неї картка (крім самого поля категорії) заблокована.

Дві додаткові узгоджені з людиною речі поверх «показати закріплене»:
1. **Розподіл по панелях + порядок** — тенант-рівневий (не per-товар) layout: кожна динамічна характеристика живе в одній з двох дропзон (`dropId` "info-panel"/"meta-panel"), порядок — drag&drop прямо на картці товару (режим «Редагувати розташування характеристик», `@dnd-kit`, той самий принцип двопанельного перетягування, що `CategoryCharacteristicsPicker`). Категорія — фіксована, поза цим механізмом. **2026-08-03:** обидві дропзони тепер візуально в одній картці — `ProductMetaPanel.tsx` видалено, її вміст (і друга дропзона "meta-panel") переїхав у `ProductInfoPanel.tsx`; сам механізм (таблиця `product_characteristic_layout`, `dropId`-и, спільний `DndContext`) не змінився, лише де він рендериться — `modules/products.md`. Постачальник — не тут, окрема вкладка «Технічні дані» (`products-technical-tab.md`).
2. **Особлива форма для двох характеристик**: «Тип тканини та матеріал» — спершу тип тканини (із закріплених значень категорії), тоді розкладка складу матеріал+% (лише з «можливих матеріалів» обраного типу, `fabric_type_possible_materials`); «Інструкція по догляду» — множинний вибір (решта динамічних характеристик — одне значення).

**Кольори/Постачальники/Розміри** мають власний UI на картці (SKU-конструктор, панель метаданих) — виключені з динамічної секції характеристик, але **другим раундом (2026-08-02) підкорені тому самому закріпленню за категорією**: Постачальник у `ProductMetaPanel` показується лише коли `suppliers` закріплено; вибір кольору/розміру в SKU-конструкторі — лише коли `colors`/відповідний `size-type:*` закріплено. Розміри в конструкторі SKU тепер — реальні значення закріплених типів розмірів (`size_types`/`size_values`), не хардкод-список `SIZE_OPTIONS`.

**Теги** — теж динамічна характеристика (не фіксований рядок на панелі): показується лише коли закріплена за категорією, ідентифікується через `system_key = "tags"` (як і раніше для `syncProductTags`), UI (чипи + dropdown + вільний ввід) той самий, що був, лише джерело реальних тегів — `custom_characteristic_values`, не хардкод-список.

**Розміри/вага посилки** (`ProductMetaPanel`) успадковують ефективне значення категорії (`categories.default_*`), коли на товарі не задано власне — той самий принцип, що успадкування налаштувань між категоріями, застосований на рівень нижче.

## Модель даних (коротко, повністю — db.md)
`products` втратила 9 колонок за два проходи (`brand`/`collection`/`season_type`/`fit`/`country_of_origin`/`manufacturer`/`material`/`fabric_type` — міграція `0029`; `brand_country` — міграція `0030`, окремим проходом після живої перевірки) — були хардкод-копіями значень, не пов'язаними з жодним довідником. `gender`/`description`/`season` лишились (не частина системи характеристик). `package_length_cm`/`package_width_cm`/`package_height_cm`/`package_weight_kg` лишились nullable-колонками без нової міграції — просто отримали нову семантику `NULL` = успадковано від категорії (той самий принцип, що `categories.default_*`).

## Відкрито
- [ ] **Не перевірено в браузері жодного з двох раундів** — пісочниця цієї сесії без доступу до localhost. Перед позначенням «готово» потрібна перевірка людиною: drag&drop між панелями, розкладка складу тканини, теги, обидві країни, гейтинг постачальника/кольору/розміру, успадкування посилки.
- [ ] У дев-БД тепер співіснують «Турція» (створено людиною вручну під час тестування) і «Туреччина» (засіяно з canonical-списку) в довіднику «Країни» — не видаляв чужий запис самовільно; людина сама вирішує, яку лишити (Settings → Довідники → Країни)
- [ ] `db:seed` не заповнює `product_characteristic_values`/`product_material_composition` для демо-товару — картка стартує з порожніми динамічними характеристиками, навіть якщо категорія закріпила якісь; перевірка руками через UI
- [ ] Бренд/Колекція в `ProductHeader` шукаються за лейблом характеристики («Бренди»/«Колекції»), не `system_key` (як «Теги») — перейменування характеристики людиною мовчки зламає показ у хлібних крихтах (прийнятний компроміс, не просили окремого маркера, `decisions.md`)
- [ ] Людина ще думає над ідеєю окремої вкладки «Додаткові характеристики» (залишити «основні» на вкладці «Основне», решту — окремо) — не робили цього разу, лишається відкритим питанням
- [ ] Заміри (`measurement-type:*`) закріплюються на категорії, але вкладка «Розміри та заміри» й далі на хардкоді (`lib/constants/measurement-types.ts`, захардкоджена `ProductSizeChart`) — не підключено цього разу, окрема задача. Розміри (`size-type:*`) уже підключено до SKU-конструктора (вище)
- [ ] Немає UI-способу скинути власне значення розмірів/ваги посилки назад на «успадковано від категорії» — той самий прийнятний компроміс, що для полів самої категорії (`decisions.md`)
