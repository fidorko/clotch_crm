# Модуль: products — піддокумент «Технічні дані» + журнал подій

Частина модуля `products` (`docs/modules/products.md`) — винесено окремо одразу при створенні (той самий привід, що `products-characteristics.md` — основний файл модуля впритул до ліміту, `CLAUDE.md` розділ 0). Статус/доступ/зв'язки — спільні з `products.md`, тут немає власного запису в `map.md`.

**Маршрут:** /products/[id] (вкладка «Технічні дані», `?tab`-параметра нема — перемикання вкладок клієнтське, `Tabs`)

## Призначення
Окрема вкладка на картці товару, куди перенесено поля, що раніше жили внизу `ProductMetaPanel` і не мали прямого стосунку до продажу/характеристик: **Створено/Оновлено/Створив/Останній редагував** (read-only), **Постачальник** (гейт закріпленням за категорією — та сама логіка, що була), **Артикул постачальника**, **Розміри (ДхШхВ)** і **Вага** посилки (успадковують ефективне значення категорії, як і раніше). Порядок полів — drag&drop, **tenant-рівнева** персистентність (`product_technical_layout`), той самий принцип, що `product_characteristic_layout` (`products-characteristics.md`), але один список без панелей.

Знизу вкладки — **журнал подій товару**: кожне збереження форми (автозбереження, `saveProduct`) діфиться проти рядка в БД ДО update — пишеться по одному рядку журналу на кожне реально змінене скалярне поле `products` (дата+час до секунди, актор, стара→нове значення), плюс разова подія «Товар створено» при вставці рядка (`createProduct`). Постачання/Продажі (номер поставки/номер замовлення) — **свідомо не додано**: відповідних модулів (`roadmap.md`) ще нема в проєкті, вигадувати поля під неіснуючі сутності не стали (пряме рішення після `AskUserQuestion`) — лишається на майбутнє, коли ці модулі з'являться.

## Модель даних (коротко, повністю — db.md)
`product_technical_layout` (tenant-рівнева, без `product_id`) і `product_activity_log` (`product_id` FK CASCADE) — обидві нові таблиці, RLS увімкнено (`tenant_isolation`, той самий патерн, що решта). `products.created_by`/`updated_by` (існували в схемі й раніше, але ніколи не заповнювались поза сідом-мокою) тепер реально пишуться (`DEV_USER.name`, `TODO(auth)` — той самий тимчасовий підхід, що dev tenantId).

## Зроблено
- 2026-08-03 — вкладка «Технічні дані» + журнал подій, перший прохід. Три уточнення через `AskUserQuestion` перед реалізацією: (1) номер поставки/замовлення — не додавати зараз (модулів «Постачання»/«Замовлення» ще нема); (2) деталізація журналу — diff по кожному зміненому полю, не один узагальнений запис на збереження; (3) порядок полів вкладки — tenant-рівнева персистентність (як у характеристик), не лише клієнтський стан. `tsc`/`eslint`/`next build` чисто; живою перевіркою в браузері (Playwright, headless Chromium) підтверджено: перенесення 8 полів у нову вкладку, drag&drop зберігається в БД і переживає повне перезавантаження сторінки (звірено прямим SQL-запитом), автозбереження пише diff-рядки в журнал з коректним `updatedBy`, подія «Товар створено» зʼявляється при «Додати товар», блокування вкладки без категорії працює так само, як раніше на `ProductMetaPanel` — підтверджено людиною

## Відкрито
- [ ] Diff журналу охоплює лише прямі скалярні колонки `products` (ціна/статус/категорія/постачальник/опис/розміри посилки тощо) — значення динамічних характеристик, складу тканини, замірів і тегів (junction-таблиці, id → лейбл резолвиться лише на клієнті) **не діфляться і не логуються** — свідомий компроміс за браку часу, не забута робота
- [ ] Постачання/Продажі (номер поставки/номер замовлення) в журналі — не додано, бо відповідних модулів ще нема (`roadmap.md`); коли з'являться — додати `eventType`/nullable-поле номера в `product_activity_log`
- [ ] Пагінація журналу — курсор по `occurredAt` рядків (не подій): якщо межа сторінки (60 рядків) випадає всередині diff-групи одного збереження, частина полів цієї групи покаже «Показати ще» лише наступним кліком — рідкісний, не критичний артефакт
- [ ] Блокування вкладки без категорії (`isDraft && !form.categoryId`) успадковує той самий давній нюанс, що й решта картки: `ProductEditorContext.initialCategoryId` мовчки підставляє `categories[0].id` як легасі-фолбек, тож на тенанті з наявними категоріями блокування фактично ніколи не спрацьовує для нового товару — не новий баг цієї задачі, лише перенесений разом з полями
- [ ] `LayoutDragCard` (перетягувана плитка-лейбл) тепер існує у двох майже однакових копіях — тут (один список) і в `DynamicCharacteristicsSection` (дві панелі) — не консолідовано, той самий клас відкритих пунктів, що `ConfirmDeleteIconButton`/`DeleteSkuButton` (`products.md`)
