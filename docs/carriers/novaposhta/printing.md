# Друк ЕН / маркування (printDocuments())

**✅ Реалізовано третім проходом** (пряма вказівка людини — «зроби все таки друк маркування»), за URL-схемою нижче — уточнена й **звірена живим запитом шостим проходом** (`orders.md`, bulk «Друк ТТН»). Офіційний портал (`developers.novaposhta.ua`) стабільно повертає 403 для автоматизованого запиту, тому URL підтверджено НЕ звіркою з офіційною документацією напряму, а незалежним відкритим SDK (`lis-dev/nova-poshta-api-2`, PHP, широко використовується — метод `printGetLink()`), плюс живим прикладом з іншої CRM, наданим людиною:

```
https://my.novaposhta.ua/orders/{printDocument|printMarking100x100}/orders/{documentRef1,documentRef2,...}/type/{pdf|html}/apiKey/{apiKey}
```

**Сегмент — `orders/`, БЕЗ квадратних дужок.** Третій прохід (перше «жива перевірка») помилково скопіював з SDK літеральний сегмент `orders[]/` (PHP-артефакт назви змінної в коментарі SDK, не частина реального шляху) — це працює для РІВНО ОДНОГО ref, але повертає **порожню відповідь**, щойно там більше одного значення через кому (підтверджено прямим запитом, шостий прохід: 1 ref — валідний PDF, 2-3 ref/ttn через кому з `[]` — порожньо). `orders/` (без дужок) коректний для 1 і для N значень, `Ref` (GUID з `InternetDocument.save`) і `IntDocNumber`/ТТН — обидва працюють як ідентифікатор, результат — один PDF з N сторінками (по сторінці на ref).

Це **не** JSON-RPC виклик до `api.novaposhta.ua` (інша модель, не через `callNovaPoshta`) — URL вище йде на `my.novaposhta.ua`. Доступно лише для вже створеного відправлення (`order.carrierShipmentRef`), тобто вже ПІСЛЯ успішного `createShipment` в тому самому замовленні.

**Восьмий прохід — apiKey більше не покидає сервер.** Раніше `printDocuments()` просто повертав рядок URL (з голим apiKey у шляху) клієнту, і `window.open(url)` відкривав його напряму — apiKey був видно в адресному рядку браузера й лишався в історії (людина показала живий приклад: посилання друку маркування з apiKey відкритим текстом). Тепер `NovaPoshtaProvider.printDocuments()` сам робить `fetch()` на цей URL СЕРВЕРНО і повертає `{ pdfBase64 }` — PDF-байти в base64, без URL. Клієнт (`SuccessPanel`/`OrderForm.tsx`, `OrderDeliveryCard.tsx`, `PrintTtnDialog.tsx`) відкриває результат через `openPdfBlob()` (`src/lib/open-pdf-blob.ts`) — декодує base64 в `Blob`, `URL.createObjectURL()`, відкриває `blob:`-URL у новій вкладці. В адресному рядку клієнта тепер лише `blob:http://localhost:3000/...`, apiKey ніде на клієнті не з'являється.

Головне: **«ЕН» (сама накладна/документ) і «Маркування» (наліпка-штрихкод на коробку) — це два РІЗНІ друковані документи**, з різними форматами.

## Друк самої ЕН (накладної)
📄 Задокументована поведінка — в особистому кабінеті друк ЕН відбувається на **A4**, з вибором:
- «2 копії» — повний аркуш A4 з двома копіями ЕН
- **«1 копія»** — на аркуші заповнена лише половина, друга половина порожня

**Формату «A5» як окремої, явно названої опції в жодному знайденому джерелі нема.** Найближчий реальний еквівалент того, що зазвичай мають на увазі під «А5» — саме режим «1 копія»: половина аркуша A4 (розміром і є фактично A5) з накладною, друга половина — порожня, не окремий менший аркуш паперу. Якщо потрібен буквально фізичний друк на аркуші A5 (не половина A4) — це питання до принтера/налаштувань драйвера друку на стороні CRM (масштабування PDF), не до самого API, і в API/кабінеті такого перемикача не існує.

## Друк маркування (наліпка на коробку)
📄 Задокументована поведінка — два реальні формати, обидва підтверджені кількома незалежними джерелами (включно з реальною сторінкою товару — самоклейкий папір для маркування продається в самої НП):

| Формат | Розмір | Для чого |
|---|---|---|
| Терморулон | **101×101 мм** (рулон на 500 етикеток, «101х101/500») | Термопринтер етикеток (в кабінеті НП рекомендують Zebra GC420d чи сумісний) |
| Аркуш A4 | **105×99 мм** на етикетку, 6 етикеток на аркуш (самоклейкий папір, реальний товар НП: «Папір А4 самокл. 105×99 мм для маркування, 6 шт. на аркуші») | Звичайний офісний принтер, без термопринтера |

У самому кабінеті пункт меню називається **«Маркування 100×100, PDF»** (колоквіальна назва, друкований розмір штрихкод-зони — 100×100мм; фізичний самоклейкий аркуш — 105×99мм, різниця — поля навколо). Масштаб друку на A4 (6 етикеток): **98%**, якщо стікер-папір із заокругленими кутами, **100%** — якщо з прямими.

**Бізнес-правило (не технічне, але важливе для CRM):** друк маркування прямо з особистого кабінету НП доступний лише клієнтам з оборотом **від 50 ЕН/місяць** — тенант з меншим оборотом такої кнопки в кабінеті НП не побачить (не стосується друку через власний API-виклик, якщо такий буде реалізований, лише ручного кабінету).

## Механізм видачі документа (як саме отримати PDF) — ✅ реалізовано третім проходом, URL-сегмент виправлено шостим, apiKey прибрано з клієнта восьмим
URL — `my.novaposhta.ua/orders/{method}/orders/{ref1,ref2,...}/type/{format}/apiKey/{apiKey}` (розділ вище, без `[]`). Піддомен `novadoc.novaposhta.ua`, згаданий у попередньому дослідженні, виявився НЕ тим механізмом — реальна робоча схема через `my.novaposhta.ua/orders/...` підтверджена незалежним відкритим SDK (`lis-dev/nova-poshta-api-2`) і прямим живим запитом (шостий прохід), не офіційним порталом напряму (403 для автоматизованого запиту). `NovaPoshtaProvider.printDocuments()` (`provider.ts`) формує цей URL і сам робить `fetch()` СЕРВЕРНО (восьмий прохід — раніше лише формував рядок і повертав клієнту), повертає `{ pdfBase64 }`; кнопки «Друк ЕН»/«Друк маркування» — у `SuccessPanel` (`OrderForm.tsx`) і bulk «Друк ТТН» (`PrintTtnDialog.tsx`), доступні лише після успішного `createShipment` того самого замовлення (`order.carrierShipmentRef`), відкривають результат через `openPdfBlob()` (blob-URL, без apiKey в адресному рядку).

До того моменту `NovaPoshtaProvider.printDocuments()` кидає `CarrierNotImplementedError` (`errors.ts`) — чесна відмова, не вигаданий URL.
