# Decisions

## Способи доставки: список окремо від конфігурації по юридичній особі
`delivery_methods` лишається списком, спільним на тенанта; ключ/відправник/платник/автоматика тощо переїхали в нову `delivery_method_entity_settings` (по одному рядку на пару спосіб×ЮО).
Чому: у кожного ФОП/ТОВ тенанта — власний кабінет перевізника (окремий API-ключ, окремий відправник), а сам факт «ми возимо Новою поштою» — один на весь магазин. Змішувати список і конфігурацію в одній таблиці змусило б дублювати рядок способу доставки на кожну юридичну особу. Побічний наслідок — форма замовлення (orders/new) тимчасово бере налаштування першої юридичної особи тенанта (`TODO(legal-entity-routing)`), поки не реалізовано явний вибір ЮО на замовленні (окрема майбутня задача — там же вирішиться, який ФОП відправляє і на чий рахунок ідуть гроші).

## Замовлення: реальні orders/customers/order_items ЗАРАЗ, список /orders лишається на моках
Форма `/orders/new` пише в реальні таблиці (тенант-скоуповано, RLS); список `/orders` — окрема задача, не переведено заодно.
Чому: людина явно обрала «реальні таблиці зараз» замість «ТТН лише в клієнтському стані сесії» (номер ЕН — реальний артефакт на акаунті Нової пошти, губити його на F5 неприйнятно); але переписування вже готового мок-списку (KPI/фільтри/bulk-дії/друк ТТН) — окремий обсяг роботи, не питали.

## CarrierProvider.ShipmentAddress → discriminated union (counterparty / new_recipient)
Замінено на `{kind:"counterparty",...} | {kind:"new_recipient",...}` під час першої реальної реалізації `createShipment`.
Чому: попередня форма (`counterpartyRef`+`contactPersonRef` для обох сторін) не мала способу описати типовий e-commerce кейс — отримувач замовлення майже завжди НОВА людина, якої ще нема серед контрагентів акаунта перевізника. Безпечно міняти форму типу — жоден код ще не викликав `createShipment` (раніше лише кидав `CarrierNotImplementedError`).

## Мітки компонентів у dev-режимі
Блоки/секції сторінки обгортаються `DevBlockLabel`, показ керується прапорцем на модуль (`lib/dev/dev-flags.ts`), вимикається разом зі зміною статусу UI на `готово`.
Чому: людина звіряє UI по скріншотах — назва компонента на екрані замість опису словами економить токени й виключає плутанину «яка це секція».

## SEO: розділення CRM і публічних сторінок
CRM-екрани (за авторизацією) — `noindex, nofollow` за замовчуванням через `metadata` розділового layout. Публічні сторінки (лендинг) отримають повне SEO окремо, коли з'являться.
Чому: мультитенантна CRM — індексація сторінок з чужими бізнес-даними є витоком даних (розділ 6 CLAUDE.md), а не просто зайвим трафіком.

## Завантаження фото товару: локальний прев'ю до підключення БД
`ProductPhotoGallery` показує вибране фото одразу (`URL.createObjectURL`), але нічого не зберігає — типи `ProductPhoto {id, url, alt}` не змінились, тож коли з'явиться бекенд, зміниться лише джерело `url` (blob → реальний), верстка й рендер-логіка лишаються тими самими.
Чому: дає реальну взаємодію зараз без зайвої роботи, яку доведеться переробляти — реальне збереження вимагає файлового сховища й таблиці в БД (ще в беклозі).

## БД: Drizzle + postgres.js, не pg
`drizzle-orm/postgres-js` + пакет `postgres` замість `node-postgres` (`pg`).
Чому: перше-класна підтримка в Drizzle, нативний TS API без окремих `@types/pg`, простіший singleton-патерн для Next.js dev-режиму (HMR). Рішення низького ризику — легко зворотне за потреби.

## БД: pricing — плоскі numeric-колонки, не jsonb
14 цінових колонок у `products` (`purchase_price`, `old_price` + 4 канали × `mode`/`amount`/`percent`) замість jsonb чи окремої EAV-таблиці.
Чому: набір полів фіксований і не тенант-конфігурований (не EAV-випадок); ціна — очікуване поле для `WHERE`/`ORDER BY` на майбутньому списку товарів, а індексувати/планувати запити по значенню всередині jsonb суттєво гірше за звичайний `numeric`. Переглянути, якщо з'являться динамічні/per-тенант цінові рівні (див. `db.md`).

## БД: RLS увімкнено одразу в першій міграції
Кожна прикладна таблиця має `ENABLE ROW LEVEL SECURITY` + політику `tenant_isolation` з першого дня, а не як окрема задача «колись пізніше». Застосунок підключається non-owner роллю `app_user` (не власником, яким котяться міграції) — інакше RLS не перевіряється жодним запитом і існує лише на папері.
Чому: ретрофіт RLS на таблиці з даними — ризикованіша операція (треба перевірити, що жоден існуючий запит не покладався на обхід RLS), ніж додати одразу; RLS не залежить від наявності авторизації — джерело `tenant_id` для сесійної змінної однаково тимчасове (dev-константа), незалежно від того, коли підключати RLS.

## БД: категорія/колекція — прибрано дублювання з TS-типу
До підключення БД `Product` мав одночасно `category`, `info.category` (повний шлях) і `breadcrumb` (масив), а `collection` дублювався з `info.collection`. Спрощено: `category` (коротко) + `categoryPath` (повний шлях, БД: `category_path`), одна колонка `collection`, `breadcrumb` більше не зберігається — рахується на рендері (`ProductHeader`) з `category` + `name`.
Чому: зберігати дублікати означало б синхронізувати кілька джерел істини при кожній зміні назви/категорії товару; дублювання в типі не мало причини — просто накопичилось по ходу верстки.

## БД: автобутстрап через `predev`, не git-хук
`npm run dev` сам піднімає Docker (`--wait`) і накочує міграції/роль (`predev` у `package.json`) — замість git-хука на `post-merge`/`git pull`.
Чому: хуки в `.git/hooks` не передаються через `git pull`/`clone` — довелось би окремо налаштовувати на кожній машині, та сама зайва дія, якої хотіли уникнути. Прив'язувати підняття Docker і зміни в БД до звичайної, зазвичай пасивної команди `git pull` — несподівана поведінка. `npm run dev` — команда, яку й так вводять свідомо перед початком роботи.

## Зображення категорій: реальне файлове сховище, на відміну від фото товару
На пряме прохання підключено зараз (не blob-прев'ю, як досі в `ProductPhotoGallery`) — диск поза `public/`/`src/` (`storage/uploads/<tenantId>/categories/`), роздача через власний route handler, а не напряму. Деталі — `db.md`.
Чому: свідомий виняток із загального принципу «відкладати реальне зберігання, поки не попросять» (`decisions.md` вище, фото товару) — тут прямо попросили зараз. Product-фото цим не зачіпаються і лишаються blob-only, це не автоматичне поширення рішення на весь проєкт.

## Зображення (категорії, товар, колір): диск → байти в БД
Спершу (категорії) робили реальне файлове сховище на диску (`storage/uploads/<tenantId>/...`) — потім перенесено на `bytea`-колонки в тих самих таблицях (`category_images`, `product_photos`, `product_color_photos`), роздача лишилась через ті самі route handlers, тільки за `id` рядка замість `filename`.
Чому: БД (Supabase) — один спільний Postgres для всіх машин розробки, диск — локальний для кожного ПК. Файли на диску губилися б при переїзді на нову машину чи для іншого розробника; байти в БД — ні, і заразом їх безкоштовно чистить каскадне видалення рядка (FK `ON DELETE CASCADE`), без окремого коду прибирання файлів.

## Зображення категорій: `tenantId` для роздачі — з сесії, не з URL
Route handler `api/uploads/categories/[filename]` бере `tenantId` через `getDevTenantId()` на сервері; `filename` у URL — опаковий UUID без вкладеного `tenant_id`. Ізоляція тенантів для файлів досягається тим, що чужий тенант шукає файл у *своїй* теці на диску (де його нема), а не перевіркою «чи цей filename належить цьому tenant_id» (такої перевірки й не потрібно).
Чому: пряма аналогія з правилом 3 розділу 6 CLAUDE.md для БД (`tenant_id` тільки з сервера, ніколи з клієнта) — застосована і до файлової системи, щоб той самий принцип не довелося винаходити наново, коли з'явиться реальна авторизація.

## Видалення категорії з дітьми: блокує сама БД (FK RESTRICT), не лише код
`categories.parent_id` — `ON DELETE RESTRICT`. `deleteCategory` ловить `error.cause.code === '23503'` (Drizzle обгортає сиру помилку `postgres.js` — код лежить у `.cause`, не на самій помилці) і повертає дружній текст.
Чому: обмеження на рівні схеми — надійніше за app-level перевірку «чи є діти» перед видаленням (немає вікна для гонки запитів, і захищає навіть якщо колись з'явиться інший шлях запису до таблиці).

## products.category_id: SET NULL, не RESTRICT (на відміну від categories.parent_id)
`products.category_id` (FK на `categories.id`) — `ON DELETE SET NULL`. Видалення категорії просто знімає прив'язку в товарів, не блокується.
Чому: інша семантика, ніж `categories.parent_id` (там `RESTRICT` — не можна видалити категорію з дітьми). Тут блокувати видалення категорії через те, що на неї посилаються товари, було б надто суворо й несподівано для власника магазину — товар просто стає без категорії, а не «застряглою» причиною неможливості прибрати застарілу категорію.

## Редагування полів-довідників у ProductInfoPanel: олівчик, а не завжди відкритий список
Категорія/Колекція/Стать/Сезон/Посадка/Виробник/Матеріал/Тип тканини — тепер «текст + олівчик → відкрити список» (новий `EditableSelectRow`), а не завжди видимий `Select`, як було. Категорія в режимі перегляду показує повну ієрархію («Одяг / Джинси»), не тільки кінцеву назву.
Чому: пряме прохання — уніфікувати з уже наявним патерном `PurchasePriceRow` (перегляд/редагування явно розділені), а не тримати два різні візуальні стилі редагування в одній панелі.

## Хлібні крихти — з реальної категорії (categoryId), не з текстового поля
`ProductHeader` рахує крихти через `getCategoryPath(categories, product.categoryId)`, а не `product.category` (застаріле текстове поле, не оновлюється автоматично при виборі категорії).
Чому: після підключення `categoryId` текстове поле `category` стало потенційно застарілим — крихти мають показувати те, що людина реально обрала, а не historical/дефолтний текст із моку/сіду.

## HeaderActions: DEV_USER — реальні ім'я/email людини, не generic-заглушка
`lib/constants/dev-user.ts` (`{ name: "Дмитро", email: "fidorko.dv@gmail.com" }`) — показуються в `UserMenu` (аватар-чіп у шапці), поки немає авторизації. Перед тим як писати — прямо спитав людину, чи вона усвідомлює, що реальні ім'я й особиста пошта потраплять у git-історію репозиторію (`fidorko/clotch_crm`, GitHub) назавжди, навіть після заміни значення. Людина підтвердила — хотіла точно так, як на її ж скріні-зразку.
Чому фіксую окремо: це свідомий виняток із типового «не вигадуй/не хардкодь особисті дані» — не мовчазне рішення асистента, а прямий, підтверджений вибір людини з озвученим ризиком. Якщо колись репозиторій стане публічним або зміниться власник — варто прибрати цей коміт із git-історії (`git filter-repo`/BFG), не просто замінити значення в HEAD.

## Постачальники: месенджери/соцмережі — справжні бренд-іконки через `react-icons`
`lib/constants/supplier-options.ts` — Telegram/Viber/WhatsApp/Facebook/Instagram/TikTok/Threads показують фірмову іконку бренду (`react-icons/fa6`, набір `Fa*`) у кружечку брендового кольору, не текстовий код.
Чому: `lucide-react` (єдина іконкова бібліотека проєкту) не має жодної брендової іконки — спершу зробив тимчасовий компроміс (кружечок з 2-літерним кодом замість лого, без нової залежності), але людина прямо попросила саме «фірмові» іконки. Погодив із людиною через питання (`AskUserQuestion`) — обрала `react-icons` замість самописних inline SVG (правило 9.9 CLAUDE.md дотримано: нову залежність не додавав без явної згоди).

## Валюти: окрема таблиця, не reference_items; курси НБУ — по кліку, не за розкладом
`currencies` — власна таблиця (код/символ/позиція/знаки після коми/курс/автооновлення), не спільний `reference_items` (той — лише «просто назва»). «Автооновлення» за замовчуванням увімкнено (`auto_update = true`), джерело курсу — публічний API НБУ (`src/server/integrations/nbu.ts`), але реального планувальника (cron) у проєкті нема — обидва виклики (одинична й пакетна кнопка «Оновити курс(и)») спрацьовують лише по кліку користувача.
Чому: додавати вигаданий/непрацюючий "автоматичний" механізм було б нечесно (виглядало б як робоче автооновлення, а насправді нічого не оновлювало б само); яку платформу деплою й спосіб планування (Vercel Cron, зовнішній тригер на API-роут тощо) використовувати для справжнього розкладу — рішення, яке варто узгодити з людиною окремо, коли з'явиться деплой, а не вигадувати мовчки зараз.

## Довідники «Характеристики товару»: дві генеричні таблиці, не enum і не нова колонка на кожну
Людина сумнівалась, чи можна дати власнику магазину самому створювати нові прості довідники («Тип комірця» → «Суцільнокрійний, Крильце, Ліхтарик») без втручання розробника — чи не знадобиться нова колонка/таблиця в БД на кожну таку характеристику. Відповідь: ні, не знадобиться. `custom_characteristics` (сама характеристика) + `custom_characteristic_values` (її значення, FK з `ON DELETE CASCADE`) — одна пара таблиць покриває довільну кількість довільно названих характеристик, без DDL при кожному створенні.
Чому не розширили натомість `reference_items.kind` (уже наявний спільний довідник для 8 «просто назва» пунктів): `kind` — фіксований pg-enum, значення задаються в коді розробником (`REFERENCE_ITEM_KINDS`). Дозволити людині вводити довільну назву характеристики в попапі означало б `ALTER TYPE ... ADD VALUE` з боку застосунку на кожен новий ввід — DDL, ініційований користувачем через звичайну форму, і Postgres до того ж не вміє `DROP VALUE` (уже наступали на це, коли `currencies` вийшов з `reference_items` — `db.md`). Дві прості таблиці — стандартний, передбачуваний шлях, той самий, що вже використаний для `tags`/`colors`, тільки з додатковим рівнем «характеристика → значення».

## Теги: перенесено з окремої таблиці tags у custom_characteristics — свідомий ризик, підтверджений людиною
Раніше `tags`/`product_tags.tag_id` — окрема таблиця з реальним зв'язком товар↔тег. За прямою вказівкою («Такі прості довідники як... Теги... також перетвори в користувацькі») перенесено в `custom_characteristics` (рядок з `system_key="tags"`) + `custom_characteristic_values`, `product_tags.tag_id` замінено на `characteristic_value_id`. Перед реалізацією прямо спитав людину: це означає переробку `syncProductTags`/`product_tags` і ризик зламати вже робоче присвоєння тегів товарам — людина підтвердила («Справді перенести в custom_characteristics»), усвідомлюючи ризик.
Наслідок, який людина також свідомо прийняла: оскільки «Теги» тепер звичайна `custom_characteristics`-характеристика, її можна видалити через кнопку-кошик у попапі, як будь-яку іншу — видалення каскадно прибирає ВСІ теги з УСІХ товарів тенанта одразу (не лише один тег). Захисту від цього навмисно не додано — послідовно з рішенням «Теги — така сама користувацька характеристика, як решта».
Технічний захист від тихої втрати даних, який усе ж додано: `updateCustomCharacteristic` переносить значення діфом (не `delete-then-insert` усього списку) — інакше кожне збереження попапу «Теги» (навіть без реальної зміни значень) переприсвоювало б `id` усім значенням і мовчки відв'язувало теги від товарів через `ON DELETE CASCADE`. Дворазова міграція (додати нове поруч → перенести дані одноразовим скриптом → прибрати старе) виконана без втрати наявних dev-даних (4 теги, 4 зв'язки товар↔тег — перевірено до і після).

## tenantId: dev-константа до авторизації, але типізований параметр з першого дня
`src/server/tenant/get-tenant-id.ts` (`DEV_TENANT_ID` з `.env`) — до появи авторизації. Сигнатури data-access шару (`src/server/data/*`) вже приймають `tenantId` як обов'язковий типізований параметр незалежно від джерела.

## Перемикачі довідника (CRM/вітрина/фільтри) для не-custom_characteristics: окрема генерична таблиця, не розширення colors/reference_items
За наступним зауваженням («ті 3 перемикачі повинні бути на всіх довідниках характеристик товару») перемикачі знадобились і для довідників групи «Характеристики товару», які не є `custom_characteristics` — спершу «Кольорів»/«Тип тканини та матеріал» (список рядків, а не один запис «на весь довідник»), а за наступним уточненням людини («не на всіх» → «Розміри та заміри», «ще інструкції») — і для «Інструкція по догляду»/«Розміри та заміри», які взагалі ще без власної БД-таблиці зі списком значень. Замість трьох нових boolean-колонок у `colors`/`reference_items` (і вигаданих колонок у таблиці, якої ще нема для двох останніх) — нова генерична таблиця `reference_dictionary_flags` (`tenant_id`, `dictionary_key`, 3 boolean, PK з обох перших колонок), ключована просто рядком, не залежна від того, чи є в довідника реальний список значень.
Чому: колонки в `colors`/`reference_items` довелось би дублювати на кожен рядок довідника (кожен колір мав би однакове значення прапорця — зайва денормалізація), а сенс прапорця — «на весь довідник», не на окремий колір/тканину; для «Інструкції по догляду»/«Розмірів та замірів» колонок у власній таблиці взагалі ще нема, куди їх додати. Окрема таблиця з ключем `dictionary_key` — той самий підхід, що вже виправдав себе для `custom_characteristics`/`custom_characteristic_values` (generic, а не колонка-на-кожен-випадок), масштабується на будь-який довідник, включно з тим, що ще не має власної таблиці, просто додаванням ключа.

## «Кольори» перенесено з окремої сторінки в попап; курсор — явний `cursor-pointer` на всіх клікабельних плитках
За прямою вказівкою: (1) `/settings/references/colors` (окрема сторінка) видалена — «Кольори» тепер плитка+попап (`ColorsTile`/`ColorsFormDialog`), як і решта довідників групи «Характеристики товару» (той самий `ColorsList` без змін усередині діалогу); (2) усі клікабельні елементи плиток «Довідники» отримали явний клас `cursor-pointer`.
Чому явний клас, а не якийсь глобальний фікс: у Tailwind v4 preflight не додає `cursor: pointer` нативним `<button>` за замовчуванням (на відміну від `<a>`) — саме тому частина плиток (посилання-`Link` на сторінки довідників) показувала «руку» при наведенні, а частина (кнопки-тригери попапів: кольори, користувацькі характеристики) — ні; людина помітила цю неоднорідність візуально. Правильний загальний фікс (перевизначити `button { cursor: pointer }` глобально в CSS-reset) не чіпали — точковий `cursor-pointer` на конкретних інтерактивних елементах безпечніший і не змінює курсор на кнопках, де це небажано (наприклад, `disabled`).

## «Тип тканини та матеріал»: окремі реальні таблиці, не розширення `reference_items`
За зразком-скріном людини («зроби такою») довідник виявився суттєво багатшим за «просто назва» (склад, можливі матеріали, сезон/розтяжність, зображення схеми, догляд) — спитав людину прямо, чи будувати окремі таблиці в БД замість поточного спільного `reference_items`; підтверджено (рекомендований варіант). Нові таблиці — `fabric_types` (сам тип) + `materials` (окремий повноцінний CRUD-довідник, не лише вкладені значення) + 4 junction-таблиці (склад/можливі матеріали/сезони/догляд, `db.md`).
Чому не розширили `reference_items.kind`: той довідник — навмисно лише «одна назва на рядок» (`db.md`), тут же потрібні структуровані зв'язки (матеріал+відсоток, багато-до-багатьох із чекбоксами) — jsonb чи розширення `reference_items` довелося б обходити прикладною логікою замість покладатись на FK/UNIQUE на рівні БД.

## «Категорії товарів» на типі тканини — свідомо не робили, за прямою вказівкою
Зразок-скрін мав чекбокси прив'язки типу тканини до категорій товару (Худі/Світшоти/Штани/Костюми/Футболки). Перед реалізацією спитав людину: прив'язати до реальної таблиці `categories`, чи окремий незалежний список — людина відповіла прямо «категорії товарів туди не додавай». Розділ у `fabric_types` не створено взагалі (ні FK на `categories`, ні окремої таблиці); поле `recommended_use` лишилось вільним текстом («Худі, світшоти, штани») замість чекбоксів.
Чому фіксую окремо: це найпомітніше явне відхилення від скріна-зразка в цьому раунді — щоб при звірці (розділ 10 CLAUDE.md) не виглядало як недогляд, а не свідомий вибір людини.

## «Рекомендації по догляду» на типі тканини — реальний тенант-керований довідник, не хардкод-список
Спочатку планував фіксований («захардкоджений») набір пунктів догляду (як і сам скрін мовчки натякав — просто список іконок). Людина уточнила окремим повідомленням просто в процесі реалізації: «...потрібно зробити ще й деякі значення інструкцій для догляду в БД з іконками, щоб потім на сторінці матеріалів обирати з існуючих» — тобто самі інструкції мають бути реальними тенант-керованими записами (назва+іконка), а фіксованим лишається лише *набір іконок-кандидатів* для пікера при створенні запису, не самі інструкції.
Чому важливо розрізняти: перше трактування («фіксований набір іконок догляду») з попереднього раунду питань і друге уточнення на перший погляд суперечать одне одному, але насправді сумісні — «фіксований набір іконок» стосується лише палітри іконок для вибору, а не самих написів/значень, які лишились повністю в БД (`care_instructions`, `db.md`). Дало змогу заразом не плодити другий незалежний механізм поруч із вже наявною порожньою заглушкою-плиткою «Інструкція по догляду» — хоч вони й лишились не об'єднаними (`modules/settings.md`, «Відкрито»).

## Сід «Матеріали» з категоріями: `onConflictDoUpdate`, не типовий `onConflictDoNothing`
Перед запуском `db:seed` для 55 матеріалів людини перевірив БД напряму — там уже була «Бавовна» (`color = '#CCCCCC'`), створена людиною вручну через UI під час попереднього ручного тестування, і реально прив'язана до одного типу тканини (1 запис у складі, 1 — у можливих матеріалах). Типовий для сідів проєкту `onConflictDoNothing` (як у `colors`/`currencies`/`brands`) лишив би цей рядок без `category` назавжди, бо конфлікт на `UNIQUE(tenant_id, name)` просто пропустив би вставку. Замінив на `onConflictDoUpdate`, що на конфлікті оновлює лише `category` — `color`/`position` наявного рядка не чіпає, реальний зв'язок з типом тканини не порушено.
Чому фіксую окремо: єдиний сід у проєкті з такою поведінкою (решта — суворо `onConflictDoNothing`), і причина не очевидна з коду без цього контексту — наступного разу, додаючи новий сід поверх довідника, куди людина вже могла щось вписати вручну через UI, варто спершу перевірити БД, а не просто копіювати `onConflictDoNothing` за замовчуванням.

## «Тип тканини»: без % складу й без прив'язки догляду — лише «Можливі матеріали»
Після побудови повної картки типу тканини (склад з %, прив'язаний догляд, зображення схеми) людина усвідомила помилку моделювання й попросила подумати, чи права вона: «тип тканини» (Футер, Кулір, Джерсі...) — це назва структури плетіння/переплетення, а не рецепт складу. Та сама структура в різних партіях постачальника чи різних товарах реально має різний % волокон — прив'язка фіксованого складу до довідника типу тканини видавала б одну випадкову партію за універсальну істину, і на кожному товарі однаково довелося б вводити реальний склад вручну. Те саме стосується догляду: реальні символи догляду на бирці залежать від фактичного складу конкретного виробу, а не від назви структури плетіння — раз склад не фіксований на рівні типу тканини, і догляд там фіксувати не можна.
Погодився з людиною й прибрав з `fabric_types`: `fabric_type_composition` (%), прив'язку `fabric_type_care_instructions`, і заразом (з того самого редизайну) `fabric_type_seasons` («Сезон не потрібен взагалі», окреме зауваження) та зображення схеми/нотатки (замінені трьома структурними полями — Лицьова/Тильна сторона, Тактильні відчуття). Лишилось тільки `fabric_type_possible_materials` — необов'язковий перелік «що типово зустрічається в цій структурі», без %, без твердження факту. Точний склад і догляд конкретного товару — майбутня властивість картки товару, не довідника (`db.md`).
Довідник `care_instructions` (назва+іконка), уже збудований і засіяний одним записом, **не видалено** — за прямою вказівкою людини лишений у коді про запас, без споживача в UI, для тієї майбутньої задачі.

## Пікер «Можливі матеріали»: груповий мультиселект-комбобокс з інлайн-створенням
Коли % склад прибрали, єдиним пікером матеріалів, що лишився, стала «Можливі матеріали» — раніше always-visible чекбокс-грід усіх матеріалів (незручно вже при 55 записах). Переробив на `Combobox` (`@base-ui/react/combobox`, `ui/combobox.tsx`) — пошук по вводу, групування за `materials.category` (`Combobox.Group`/`Combobox.GroupLabel`/`Combobox.Collection`, додані до спільної обгортки вперше — `ui-kit.md`), інлайн-створення нового матеріалу через синтетичний `value` (`"__create__"`), перехоплений в `onValueChange` до звичайного шляху вибору.
Чому саме так: людина явно описала бажаний UX («зверху пустий інпут — починаю писати, починає шукати; можна додати прям звідти новий матеріал»), і оскільки категорії матеріалів (`materials.category`) вже існували в БД (попередній раунд — сід 55 матеріалів), природно було одразу застосувати групування, а не лишати плоский список.

## «Тип тканини та матеріал»: без окремої сторінки — усе попапами з плитки
Одразу після побудови сторінки з двома вкладками людина уточнила: «попап залишаємо, а саму сторінку... можна видалити і одразу відкривати попап для створення та редагування». Прибрано `/settings/references/fabric-materials` цілком (разом з `FabricMaterialsWorkspace`/`FabricTypesTab`/`FabricTypesList`/`FabricTypeDetailPanel`) — плитка «Тип тканини та матеріал» у гріді «Довідники» тепер показує наявні типи чіпами (`FabricTypesTile`), кожен чіп — окремий тригер `FabricTypeFormDialog` у режимі edit; «+Додати» — той самий попап у режимі create. Питав людину прямо, де тоді бачити/обирати існуючі типи без сторінки — відповідь «Чіпи типів прямо на плитці» підтвердила цей напрям.
Видалення типу тканини переїхало в сам попап (кнопка в футері `FabricTypeFormDialog`, видима лише в режимі edit) — раніше жило в `FabricTypeDetailPanel`, якого більше нема. Довідник «Матеріали» (CRUD, колишня вкладка `MaterialsTab`) з тієї самої причини переїхав усередину `FabricTypeFormDialog` як згортана секція «Керувати довідником матеріалів» (перейменовано на `MaterialsManager`) — за прямою відповіддю людини на питання «де його місце» («усередині того ж попапу типу тканини»).
Чому не лишили окрему сторінку взагалі без вкладок: людина явно попросила прибрати сторінку як таку, не спростити її — весь принцип «Довідники» вже й так керується попапами прямо з плиток (`ColorsTile`/`CustomCharacteristicTile`), і «Тип тканини та матеріал» тепер узгоджений з цим самим патерном, а не є винятком з окремим маршрутом.

## «Можливі матеріали»: за замовчуванням усі, плюс масові дії
За прямою вказівкою: у новому типі тканини `possibleMaterialIds` ініціалізується повним списком наявних матеріалів (не порожнім) — власник магазину звужує список сам, а не збирає його з нуля. Додано «Обрати всі»/«Зняти всі» в `FabricTypePossibleMaterialsField` для швидкого масового керування (актуально вже при 55 матеріалах у довіднику). При редагуванні наявного типу — як і раніше, використовується збережений вибір, не перезаписується на «всі» повторно.

## Токен-економія доків: винесено одноразові блоки з CLAUDE.md, розрізано settings.md на піддокумент
За прямим проханням людини оцінити token-економію документації: `CLAUDE.md` (читається щосесії назавжди, 241 рядок) тримав два блоки, які відпрацювали своє — розділ 1 (інтерв'ю старту проєкту, одноразовий, `stack.md`/`design.md` уже існують) і розділ 5 (повний шаблон нового модуля, потрібен лише в момент створення модуля). Винесено в `docs/_init-interview.md`/`docs/_module-template.md`, у `CLAUDE.md` лишились рядки-посилання — 241 → 175 рядків. Заразом `docs/modules/settings.md` уже фактично перевищував власний ліміт (129 рядків проти заявлених 120, розділ 0) — блок «Постачальники» (15 рядків «Файли» + 4 записи «Зроблено», самодостатня підобласть без зв'язків з рештою модуля) винесено в `docs/modules/settings-suppliers.md`.
Чому важливо: раніше правила розділу 0/9 не мали явного механізму «доку теж можна різати», лише код (правило 9.6). Додано симетричне правило (сам текст — `docs/_module-template.md`, розділ «Коли модуль переріс ліміт») і виняток у правилі 9.4 — щоб наступного разу, коли будь-який файл модуля знову впреться в ліміт, це вже мало стандартний, а не імпровізований шлях. Так само додано правило скорочення для `roadmap.md` (розділ 0) — він росте лише знизу без стелі, на відміну від файлів модуля, і з часом став би тим самим always-read баластом; сам roadmap.md сьогодні не чіпали, він ще не впритул до проблеми.
Другий раунд (той самий день, окреме питання людини): `db.md` (206 рядків, 19 таблиць, кожна за заголовком `### <table>`) структурно вже готовий до точкового читання, але правило розділу 4 казало просто «читай db.md» — тому весь файл читався навіть під задачу по одній таблиці. Замінено на «grep заголовок конкретної таблиці → читай лише її розділ», без зміни самого db.md.
Третій раунд: людина запитала, чи не варто дробити файл модуля на кілька файлів (окремо «Файли», окремо «Зроблено» тощо) для кожної сторінки. Вирішили — ні, для всіх модулів заздалегідь не варто: файл модуля й так капнутий на 120 рядків, а дроблення додає ризик «доки розійшлися» (правило 9.10) і зайву синхронізацію в кроці 3 без пропорційного виграшу. Замість фізичного дроблення — той самий трюк, що з `db.md`: секції файлу модуля йдуть у фіксованому порядку (`_module-template.md`), тож можна вибірково читати «Файли»+«Відкрито» (`offset`/`limit`), пропускаючи «Зроблено» (найбільшу за обсягом секцію), коли задача не потребує історії.

## «Розміри та заміри»: 2 незалежні прості довідники з типами, не одна таблиця-матриця
Перша спроба (та сама сесія, до підтвердження людиною) — єдина таблиця `sizes`: рядок = розмір («M») + 6 колонок замірів (обхват грудей/талії/стегон, джинси, UA/RU, EU), редагована таблиця в попапі — пряма заміна колишнього хардкоду `ProductSizeChart.tsx`. Людина відхилила після демонстрації: «Розміри» й «Заміри» мають бути двома окремими сутностями, не пов'язаними між собою (одна — можливі розміри, друга — можливі заміри), і кожна ще й ділиться на типи (розміри: одяг літерний/числовий, взуття, джинси, бюстгальтери; заміри: різні для сукні/взуття/верхнього одягу), із проханням «погуглити» реальні типи й додати найпоширеніші значення — без жодної таблиці-матриці, «просто довідник».
Перебудовано на `size_types`/`size_values` + `measurement_types`/`measurement_values` — той самий "тип → список значень" патерн, що вже є в проєкті (`custom_characteristics`, `fabric_types`), тільки без 3 boolean-прапорців і без зв'язку з `product_tags` (тут це чисто довідникові списки, не характеристики товару). Типи — тенант-керовані (людина підтвердила: власник додає свої, не фіксований enum, як `fabric_stretch`). UI лишився одна плитка «Розміри та заміри» з попапом, але тепер 2 вкладки (`Tabs`) замість однієї таблиці — теж підтверджено з людиною, а не вигадано.
Чому фіксую окремо: показовий приклад, чому для нестандартних довідників (не «просто список назв») варто спершу звірити структуру, а не одразу писати схему — перша модель здавалась логічною заміною хардкоду, але не відповідала тому, як людина подумки ділить дані (незалежні сутності з підтипами, не одна плоска таблиця). Стару таблицю `sizes` видалили окремою міграцією (спершу чистий `DROP TABLE`, тоді окремо 4 нових `CREATE TABLE`) — одночасний drop+create зі схожими іменами (`sizes`→`size_types`) провокує drizzle-kit ambiguous-rename prompt, той самий прийом, що вже задокументований для `0020`→`0021` (`db.md`, «fabric_types»).
Другий раунд того самого зауваження: назва типу в картці (`TypeGroupCard`) спершу була always-open `Input` — людина попросила «текст + олівчик», як у `ProductInfoPanel`, і прямо попросила зафіксувати це як загальне правило. Записано в `ui-kit.md` («Правило: рідко змінюваний текст — перегляд + олівчик»), `EditableTextRow` розширено опційним `label` (без нього — просто «значення + олівчик», для заголовків карток, не тільки рядків форми). Явний виняток — компактні списки швидкого масового редагування (`ColorsList`/`MaterialsManager`/`CareInstructionsList`/`SizesList`), де always-open поле лишається свідомим вибором, підтвердженим людиною саме зараз — не чіпав.

## «Закріплення характеристик»: один текстовий ключ на 9 джерел, зберігаються лише винятки
Категорія має закріплювати характеристики й значення з **9 різних за формою джерел**: 3 «прості» довідники (Кольори/Тип тканини/Догляд), 2 з вкладеною структурою тип→значення (Розміри/Заміри, кожен тип — окрема характеристика, підтверджено з людиною через `AskUserQuestion` перед кодом — щоб не повторити рольбек `sizes`/`fabric_type_composition`), довільна кількість `custom_characteristics`, і 3 «Системні» довідники (Виробники/Країни/Постачальники), додані людиною окремою реплікою вже під час реалізації. Замість FK на кожне з 9 джерел (чи 9 окремих junction-таблиць) — той самий прийом, що вже виправдав себе в `reference_dictionary_flags`: один довільний текстовий `characteristic_key` (`"colors"`, `"custom:<uuid>"`, `"size-type:<uuid>"`...), дві генеричні таблиці на всі джерела одразу.
Друге рішення в парі з першим: обидві таблиці зберігають **лише винятки** з умовчання «увімкнено все / притаманні всі значення» (людина прямо сформулювала цю умову: «за замовчуванням обрані всі, але можна деякі відключати») — не повний список станів. Наслідок: нове значення довідника (новий колір, нова власна характеристика) автоматично притаманне вже існуючим категоріям без бекфілу, і новий custom_characteristics одразу видно в картці категорії — дані тягнуться заново при кожному рендері (`buildCategoryCharacteristicOptions`), не кешуються окремим списком, що людина попросила окремо перевірити.
Чому фіксую: показовий приклад протилежного до `sizes`/`fabric_type_composition` випадку — тут неоднорідність джерел не привід городити 9 окремих таблиць чи змушувати людину вибирати «одну universal модель значення», а привід звести неоднорідність до одного текстового ключа й дозволити кожному джерелу лишатись у своїй природній формі.

## Успадкування налаштувань категорії від батьківської — nullable-колонки, а не окремі "override"-таблиці/прапорці
Людина сформулювала правило одним реченням: «всі налаштування старшої категорії успадковують молодші, при створенні й при редагуванні; але якщо я редагую молодшу — відмінність зберігається». Звірив масштаб заздалегідь через `AskUserQuestion`: які саме поля (перемикачі показу + вага/розміри за замовчуванням — не назва/опис/зображення/SEO), чи входить щойно зроблене «Закріплення характеристик» (так, той самий ланцюжок), чи потрібен видимий індикатор «успадковано/власне» (ні — досить, щоб показувалось ефективне значення).
Для 3 перемикачів (`is_active`/`show_in_storefront_section`/`show_in_header_menu`) — прибрано `NOT NULL DEFAULT true`, колонки стали nullable: `NULL` = не задано тут, успадкувати від найближчого предка з явним значенням (walk up `parent_id`). Вага/розміри за замовчуванням уже були nullable — нової міграції не знадобилось, лише нова інтерпретація існуючого `NULL`. Обрано НЕ окрему "is_overridden"-колонку на кожне поле й НЕ окрему override-таблицю — сам факт "значення явно задане" вже однозначно кодується наявністю не-`NULL`, зайва колонка дублювала б ту саму інформацію.
«Закріплення характеристик» (запис вище) довелось переробити: перша версія читала стан лише в межах ОДНІЄЇ категорії з дефолтом «все увімкнено» — не батьківський ланцюжок, яким людина явно попросила зараз. Виявилась і прихована вада моделі «двох незалежних таблиць на винятки» (`category_characteristics` для enabled, `category_characteristic_excluded_values` для значень окремо): якщо категорія лише клацнула чип (не перемикач), рядка в `category_characteristics` не з'являлося — і при спадкуванні від батька неможливо було б відрізнити «дитина взагалі нічого не чіпала для цієї характеристики» від «дитина explicitly вибрала не виключати жодного значення», обидва виглядали б як «нема власного enabled-рядка». Виправлено: `enabled` і повний набір `excludedValueIds` тепер завжди пишуться РАЗОМ, одним викликом (`setCategoryCharacteristicOverride`) — наявність рядка в `category_characteristics` стала єдиною достатньою ознакою «власне».
Чому фіксую: (1) приклад, коли `NULL` на колонці, що раніше означала лише «не задано», можна безпечно перевизначити на «успадковано» без нової сутності в схемі — але тільки якщо старим даним такий новий сенс не зашкодить (тут не зашкодив: усі наявні категорії й так мали явні `true`/`false`, лишились «власними»); (2) приклад на "будь-яка часткова дія повинна писати повний узгоджений стан, а не одне поле" — коли два незалежно записувані поля разом визначають "чи є взагалі власне налаштування", запис їх нарізно створює нерозрізнювані стани.

## «Закріплення характеристик»: перероблено з карток-перемикачів на drag&drop за макетом людини, додано @dnd-kit
Людина принесла готовий макет-скрін і детальний промпт (стиль Notion/Linear/Stripe Dashboard): дві панелі, ліва — усі характеристики компактними рядками (drag handle + назва + бейдж кількості), права — закріплені картки з чипами значень (перші 4–5 + «+N») і кнопкою ✕. Прямо заборонені: перемикачі on/off, «Обрати всі»/«Зняти всі», стрілки сортування, кнопка «Додати характеристику» — порядок і належність визначає лише drag&drop.
Це не просто рестайлінг — макет прибирає рівень деталізації «які саме значення притаманні» (чипи-виключення з попереднього раунду). Звірив три речі заздалегідь через `AskUserQuestion`, а не вигадав: (1) попап «+N» — лише перегляд, без можливості вимкнути значення (отже `category_characteristic_excluded_values` стає незатребуваною і прибирається, а не лишається мертвим кодом); (2) потрібна нова залежність для drag&drop — погоджено `@dnd-kit/core`+`@dnd-kit/sortable`+`@dnd-kit/utilities` (правило 9.9 CLAUDE.md, у проєкті досі не було DnD-бібліотеки; обрано над самописним HTML5 draggable — менше коду, готові плавні анімації й touch-підтримка); (3) порядок закріплених характеристик зберігається в БД — нова колонка `position` на `category_characteristics`.
Модель БД спростилась разом зі спрощенням UI: `category_characteristics.enabled` і вся таблиця `category_characteristic_excluded_values` видалені (`db.md`), лишилась одна таблиця «характеристика закріплена за категорією, у такому порядку». Ownership (успадковує чи має власний список) тепер на рівні ВСЬОГО списку категорії, не по кожному ключу окремо — будь-яка дія в drag&drop записує повний список одним викликом (delete-then-insert), а не апдейтить один рядок; простіше й точно відповідає інтерфейсу, де людина керує одним впорядкованим списком, а не набором незалежних перемикачів.
Заразом нова вкладка «Характеристики» на сторінці категорії (`Tabs`, поруч з «Основне») — попередній раунд свідомо ставив картку в тій самій формі («Картка в тій самій формі» була відповіддю на тодішнє питання), людина зараз попросила окрему вкладку; і явне «Зберегти»/«Скасувати» з локальним драфтом — свідомий виняток з автозбереження, яким живе решта «Довідників» у проєкті, бо так намальовано в макеті.
Чому фіксую: приклад, коли зроблена й уже перевірена функціональність (виключення окремих значень) правильно викидається повністю, а не ховається/лишається неактивною в БД — людина принесла новий, чіткіший намір (готовий макет), і краще прибрати зайву модель одразу, ніж тримати мертву таблицю «про запас» без наступного кроку, який би її використав.

## БД: переїзд з локального Docker Postgres на Supabase (hosted) — дані спільні на всіх ПК
Людина прямо попросила спробувати, щоб дані БД були однакові на всіх її ПК, а не в окремому Docker-контейнері на кожному. `DATABASE_URL`/`APP_DATABASE_URL` тепер вказують на Supabase (Session pooler, IPv4 — пряме підключення `db.<ref>.supabase.co` резолвиться лише в IPv6 і таймаутило в мережі людини). `predev` (`package.json`) більше не піднімає `docker compose up -d --wait` автоматично — попередній запис вище («автобутстрап через predev») лишається чинним для `db:migrate`/`db:setup-role`, лише крок з Docker прибрано; `docker-compose.yml` не видалено, лишається офлайн-фолбеком, запускати вручну за потреби.
Чому не одразу VPS (`stack.md` раніше планував VPS як «Хостинг далі»): людина уточнила — інтернет у неї завжди є, і поки Supabase не гірший за Docker по функціоналу, лишаємось на ньому; VPS — коли впремося в реальні ліміти (обсяг/ціна), не заздалегідь. `stack.md` оновлено: «Хостинг зараз» → Supabase, VPS — план на потім, а не поточний стан.
Non-owner роль `app_user` під Session pooler створювалась з тимчасово підміненим (лише для одноразового виклику `db:setup-role`, без правок `.env`) `APP_DATABASE_URL` без pooler-суфікса `.{project-ref}` — інакше скрипт (бере ім'я ролі буквально з username урла) створив би роль з іменем `"app_user.edgqipyltkrlvgniurvd"`, а pooler автентифікує, відрізавши суфікс, і шукав би просто `app_user`. Деталі підключення — `env.md`.

## Закріплені характеристики категорій: «останнє редагування виграє каскадом», не «дитина назавжди зберігає власне»
Людина живим тестуванням виявила: змінила закріплені характеристики на батьківській категорії («Одяг»), а дочірня («Шорти», яка раніше зберігала власний, відмінний список) не оновилась. Це була не помилка коду, а точно та поведінка, яку раніше свідомо узгодили («якщо редагую дитину — відмінність зберігається назавжди», той самий принцип, що й для класичних полів вага/розміри). Пояснив це людині прямо й запитав, чи це справді бажана інша модель — людина сформулювала нове правило двома конкретними прикладами: редагування старшої категорії каскадить усім молодшим і їхнім товарам; редагування наймолодшої каскадить лише її товарам. В обох випадках — лише з попередженням.
Це свідома зміна архітектури, а не розширення: попередня модель («дитина, що хоч раз зберегла власний список, більше не залежить від батька») — скасована повністю для закріплення характеристик. Класичних полів (перемикачі показу, вага/розміри за замовчуванням) це рішення НЕ стосується — там модель «дитина редагує — назавжди власне» лишається чинною, людина уточнювала саме про характеристики.
Реалізація: `setCategoryPinnedCharacteristics` тепер приймає `cascadeToCategoryIds` (усі нащадки, `getDescendantIds`) і при збереженні перезаписує (delete-then-insert) той самий список одразу всім їм, не лише редагованій категорії — без винятку для тих, хто мав інший власний список. Товари нічого не зберігають самі (читають список зі своєї `category_id` через уже наявний `resolveCategoryPinnedCharacteristics`-подібний шлях у картці товару), тож каскад до товарів — природний наслідок, не окремий запис. Попередження — `Dialog` перед кожним збереженням (не лише коли є діти — редагування навіть листової категорії одразу зачіпає її товари, тому попередження завжди).

## «Закріплення характеристик» категорії: прибрано попередження-Dialog перед каскадом, теж автозбереження
Одразу після впровадження автозбереження для «Основне» товару/категорії (запис нижче) людина побачила, що у вкладці «Характеристики» досі лишилась кнопка «Зберегти» — навмисний виняток, який я явно обґрунтував (drag&drop, кожен проміжний стан ще не остаточний намір, а сам каскад на дочірні категорії — ризикована дія для автоматичного спрацювання). Прямо запитав людину, чи це справді свідома зміна ризикованої поведінки (не технічна дрібниця) — підтверджено «хочу».
Реалізовано так само, як інші автозбереження: кожна ЗАВЕРШЕНА дія drag&drop (`handleDragEnd`, відкріплення ✕ — тобто реальна зміна `pinnedKeys`, не кожен проміжний `dragover`) — природна точка commit, і саме на ній автоматично спрацьовує збереження й каскад на нащадків, без Dialog-підтвердження. Це узгоджено з тим самим принципом «commit = природна точка автозбереження», що вже застосований до полів-рядків (blur) і `Select`/`Switch` (вибір) — сам drag&drop і є такою точкою: людина явно відпускає картку в конкретне місце, це не проміжний стан.
Компенсація за втрачене попередження: замість блокуючого `Dialog` перед кожним збереженням — постійний, не блокуючий текстовий натяк у підзаголовку картки, коли в категорії є діти («застосовується одразу до всіх підкатегорій...») — людина бачить наслідок ЗАЗДАЛЕГІДЬ, поки ще тільки дивиться на картку, а не як переривання просто перед кожним збереженням.

## Автозбереження форм редагування замість кнопки «Зберегти» — загальне правило проєкту
Людина помітила неоднорідність: частина даних (SKU, фото) зберігається одразу, частина (форма товару/категорії) — лише по кнопці, і саме через це минулого разу непомітно «загубилась» ProductMeasurements (ніде не зберігала змін). Початковий запит — заборонити перехід зі сторінки з незбереженими змінами й показати попап з діфом «було → стало». Обговорив дві архітектурні межі через `AskUserQuestion`: (1) рівень деталізації діфу для складних полів (ціни/характеристики/сітка замірів/теги) — узгоджено «прості поля точний діф, складні — просто назва секції»; (2) Next.js App Router не має надійного способу перехопити кнопку «Назад» браузера (лише кліки по посиланнях у застосунку) — узгоджено не намагатись.
Перш ніж це реалізовувати, людина сама запропонувала кардинально простіший напрям — автозбереження всюди, без кнопки взагалі (як уже працюють усі довідники: кольори/матеріали/типи тканини). Це не просто простіше в реалізації — воно усуває саму проблему («незбережені зміни при виході») архітектурно, а не попереджає про неї. Уточнення від людини: не debounce-поки-набираєте, а збереження одразу після виходу з інпуту (blur) — що вже й так є природною точкою "commit" у наявних компонентах-рядках (`EditableTextRow`/`EditableSelectRow`/`EditableNumberRow` — вони самі тримають чернетку під час набору, до `onChange` доходить лише вже завершене значення). Реалізовано в `ProductEditorContext.setField` і в `CategoryForm` (ефект, що стежить за всіма власними полями категорії) — обидва лише додають короткий (500мс) debounce НЕ для очікування завершення набору тексту, а щоб згладити кілька майже одночасних змін в один мережевий запит.
Свідомий виняток — «Закріплення характеристик» категорії: там кожен проміжний стан перетягування ще не те, що людина «хоче зберегти», а сам каскад на всіх нащадків — надто ризикована дія для автоматичного спрацювання на кожен рух миші під час drag&drop. Лишається з явною кнопкою «Зберегти» і попередженням про каскад.
Точкове «вібрування»/підсвітка конкретного щойно збереженого поля (простіша альтернатива діфу, яку теж пропонувала людина, «якщо важко») — не реалізовано в цьому проході: вимагало б плюс не лише в контексті, а в кожному полі-споживачі окремо (`ProductInfoPanel`/`ProductMetaPanel`/`ProductSizeChart`, CategoryForm) — загальний індикатор `saveStatus` у хедері вважали достатнім для цього проходу, лишили як відкритий пункт, якщо після пробного використання людина захоче деталізації.
Правило зафіксовано загально в `conventions.md`, не лише для товару/категорії — щоб надалі нові форми ручного редагування в проєкті теж робились автозбереженням за замовчуванням.

## Розмірна сітка товару: реальна таблиця «розмір × точка заміру», замінила нефункціональну ProductMeasurements
Людина попросила зв'язати вкладку «Розміри та заміри» картки товару з реальними даними: рядки розмірної сітки (`ProductSizeChart`) — тільки розміри, вже додані в конструкторі SKU; колонки — тільки точки заміру, закріплені за категорією товару; значення вводяться на перетині. Перед реалізацією дослідив код і виявив, що `ProductMeasurements`/`SkuMeasurementsDialog` (плаский список замірів на товар, без розміру) **ніде фактично не зберігали зміни** — жодного Server Action не існувало, лише локальний `useState`, що скидався при перезавантаженні сторінки; це не було задокументовано як відкритий пункт, хоча по факту функціонал не працював. Уточнив через `AskUserQuestion`: чи прибрати `ProductMeasurements` повністю замість сітки, чи лишити обидва — підтверджено «прибрати, замінити сіткою». Друге питання — значення сітки зберігати одразу по клітинці чи разом з рештою форми — підтверджено «разом, одна кнопка «Зберегти»» (той самий патерн, що теги/динамічні характеристики/склад тканини, `ProductEditorContext`).
Нова таблиця `product_size_measurements` замінила `product_measurements` (яка не мала виміру розміру взагалі). `size` — вільний текст, той самий рядок, що `product_skus.size` (розміри товару свідомо не FK, `db.md`) — не міняв цей давній компроміс заради узгодженості. `measurement_value_id`, натомість, **реальний FK** на `measurement_values.id` — на відміну від `product_skus.size`/колишнього `product_measurements.type` (де FK уникали через багатоджерельну неоднозначність chracteristic_key), тут джерело точок заміру рівно одне (закріплені за категорією типи замірів), тож FK доречний і безпечніший за копію вільного тексту.
На місці колишньої `ProductMeasurements` (права колонка вкладки) — людина попросила «блок з довідкою»; уточнив через `AskUserQuestion` — статичний текст чи ілюстрація/схема заміру; підтверджено ілюстрацію. Реалізовано best-effort: `MeasurementGuide.tsx` підбирає одну з кількох намальованих inline-SVG схем (обхват грудей/талії/стегон, ширина плечей, довжина рукава/виробу, довжина стопи) за ключовим словом у назві точки заміру — той самий принцип, що `CharacteristicIcon` для характеристик категорій (значення `measurement_values` вводить власник магазину вільним текстом, точного довідника-джерела для зображення нема, тому підбір за смислом назви, не строгий id). Це не технічна викрійка, а орієнтовна схема — свідомий компроміс, професійних diagram-асетів чи фотографій не було й не шукали.
Міграція `product_measurements`→`product_size_measurements` — два окремі проходи `drizzle-kit generate` (спершу схема без нової таблиці → чистий DROP, тоді повернув таблицю → чистий CREATE), той самий прийом уникнення ambiguous-rename інтерактивного промпту (не працює без TTY), що вже задокументовано для `fabric_types`/`sizes`→`size_types`. 4 рядки старої таблиці (сід демо-товару, тестові дані без розміру) не переносились — несумісні зі новою моделлю (нема виміру розміру), і сама функціональність, що їх показувала, не працювала однаково.

## Довідники «Розміри та заміри» / «Тип тканини та матеріал»: розділено на окремі скрізь, за прямою вказівкою
Людина попросила розділити два довідники, що раніше були об'єднані на рівні UI-плиток: «Розміри та заміри» (одна плитка, попап з 2 вкладками) і «Тип тканини та матеріал» (одна плитка, «Матеріали» — згорнута секція всередині попапу типу тканини). Перед реалізацією уточнив через `AskUserQuestion` два нюанси, щоб не вигадати зайвий обсяг роботи: (1) чи «Матеріали» стають повністю окремою плиткою з власним CRUD, чи лишаються секцією всередині картки типу тканини (просто перейменованою) — підтверджено «повністю окремі», за зразком «Кольорів»; (2) чи перейменування характеристики «Тип тканини та матеріал» → «Тип тканини» в «Закріпленні характеристик» вимагає міграції даних (`characteristic_key` = `"fabric-materials"`) — підтверджено «ні, лише лейбл», ключ лишається тим самим, тому жодна вже закріплена характеристика категорії чи вже введене значення на товарі не постраждали.
«Розміри»/«Заміри» на рівні даних НІКОЛИ не були одним довідником — `size_types`/`measurement_types` завжди 2 незалежні таблиці (`decisions.md`, попередній запис про відхилену єдину матрицю `sizes`), об'єднаною була лише навігація (1 плитка, 1 попап з `Tabs`). Тому розділення тут — суто UI: нові `SizesTile`/`MeasurementsTile` + `SizeTypesFormDialog`/`MeasurementTypesFormDialog`, старі `SizesMeasurementsTile`/`SizesMeasurementsFormDialog` видалені. Новий `reference_dictionary_flags.dictionary_key = "sizes"` — вільний текст без enum, підключається без міграції схеми, просто новий рядок у списку ключів (`page.tsx`, `listDictionaryFlags`).
«Тип тканини»/«Матеріали» — тут довідники й раніше були окремими таблицями (`fabric_types`, `materials`, зв'язані через `fabric_type_possible_materials`), об'єднаним був лише попап. `MaterialsManager` (CRUD) переїхав із згорнутої секції в `FabricTypeFormDialog` у власну плитку+попап (`MaterialsTile`/`MaterialsFormDialog`, новий `dictionaryKey="materials"`) — `FabricTypeFormDialog` і далі приймає `materials` (потрібен для «Можливі матеріали», зв'язок типу тканини з матеріалами не зникає, зникла лише спільна точка керування довідником). Лейбл характеристики картки товару/категорії (`characteristic-options.ts`, ключ `fabric-materials`) скорочено до «Тип тканини» — точніше відображає суть (це вибір типу тканини, склад матеріалів — окрема розкладка з %, `product_material_composition`).

## «Видалити» фактичне надходження — скасовано попередню заборону
Восьмий прохід `warehouse-receiving.md` фіксував пряму вказівку людини: видаляти можна лише планові документи, фактичні — ні. Новою прямою вказівкою (список надходжень, колонка «Дії») це скасовано — тепер видаляються обидва типи. Оскільки прийняте фактичне надходження вже могло поповнити `product_skus.stock`, видалення документа тепер спершу відкочує залишок за кожною позицією (`sum(received)` per SKU), потім видаляє сам документ (позиції — каскадно, FK `onDelete: cascade`). Якщо частину поповненого залишку вже витрачено деінде (майбутній модуль продажів) — відкат впаде на `CHECK (product_skus_stock_nonneg)`, користувачу показується пояснення замість тихого падіння.
Чому фіксую окремо: пряма відміна раніше задокументованого «пряма вказівка людини» — щоб при звірці (розділ 10 CLAUDE.md) було видно, що це свідома зміна рішення, а не розбіжність коду й доки.

## Надходження: один документ замість пари planned/actual — повний редизайн
День потому як зафіксували скасування заборони видаляти фактичне (запис вище), людина попросила переглянути весь підхід: замість двох зв'язаних документів (плановий → кнопка «Прийняти на склад» → окремий фактичний з `based_on_id`) — **один документ на надходження**, який або одразу «в процесі приймання» (просте/швидке), або спочатку «Очікується поставка» і проходить через явну машину станів. Наявні документи (включно з тестовими `RCV-2026-00x`) видалено без міграції — пряма вказівка людини, «наявні пари можна видалити».
Перед реалізацією — два раунди уточнюючих питань (мінімум 10 кожен), потім `EnterPlanMode`/`ExitPlanMode` з повним планом (схема/сервер/UI/PDF), бо зміна зачіпає схему БД (дроп `type`/`based_on_id`, enum) на спільному Supabase dev-інстансі — ризикована зміна, окрема гілка `feature/warehouse-receiving-v2` (CLAUDE.md розділ 8).
**Машина станів** (`receiving_documents.status`, спрощено людиною до 4 значень): `awaiting_delivery` (лише для `is_planned`, від створення до «Прийняти на склад») → `in_progress` (від accept для планового, від створення для простого — до фіналізації) → `completed`/`completed_with_discrepancy` (розбіжність — лише для планового, якщо хоч один `ordered !== received`). `is_planned` — фіксується один раз при створенні (два входи зі списку: «Планове надходження»/«Швидке надходження»), ніколи не редагується — людина підтвердила «заборонити перемикання», коли спитав про сценарій зміни після початку сканування; оскільки блок сканування взагалі неактивний до явного створення документа (нова кнопка «Створити надходження», окрема від колишньої лінивої create-on-first-write), конфліктний сценарій фізично неможливий.
**Лог приймання** (`receiving_document_item_events`, нова таблиця) — по прямій вказівці «треба логування приймання кожного SKU бо дати приймання будуть різні» (постачальник може довідправити частинами). Пише лише `received` (не `ordered`) при кожній зміні, без UI зараз («поки просто писати в БД про запас» — підтверджено).
**Персистенція — свідомо БЕЗ зміни** підходу: людина спершу висловила занепокоєння частими запитами до БД і запропонувала локальний кеш до явного «Зберегти прогрес», але при прямому питанні («скан = один запит, ручне редагування вже з debounce 500мс — чи це і є та ефективна модель?») підтвердила «як зараз, рекомендую» — тобто занепокоєння стосувалось гіпотетичного «на кожну клавішу» автозбереження, не наявного debounce-патерну. Реальна зміна — лише явна дія створення документа (раніше не існувала) і явна незворотна фіналізація («Зберегти документ надходження та завершити», `completeReceivingDocument`).
**Акт приймання-передачі** — реальний PDF A4 (`server/warehouse/receiving-act-pdf.ts`, `pdf-lib`+`fontkit`, той самий підхід кирилиці, що PDF-етикетки), доступний лише після фіналізації (`completedAt`), для обох видів надходження (підтверджено — не лише планового, де раніше жила заглушка «Дублювати документ»). Отримувач у шапці акту — мок-плейсхолдер, дані прийдуть із майбутніх налаштувань магазину. **Regular-вага шрифту Inter не додана** — у сесії не було надійного способу дістати бінарний файл шрифту (мережевий фетч під бінарні файли не підходить), тому акт увесь жирним (`Inter-Bold.woff2`, той самий файл, що етикетки) — відкритий пункт.
**Guard незбережених змін** — за прямою вказівкою обмежено лише сторінкою створення (до кліку «Створити» документа фізично не існує, є що втрачати); на сторінці самого документа кожна дія і так пише в БД одразу (immediate/debounce), тож типового «unsaved» стану там нема — навмисно не чіпали `beforeunload`/кнопку «Назад» браузера, та сама раніше узгоджена межа (Next.js App Router не дає надійного способу).

## Надходження: оприходування відкладено до «Завершити», гейт-на-створенні прибрано
Тим самим днем людина попросила ще один раунд змін поверх щойно зробленого редизайну (запис вище). Три пов'язані зміни:
**1. Реальне оприходування на склад — лише при «Завершити».** Раніше кожен скан/ручна зміна «Прийнято» одразу додавали дельту до `product_skus.stock` (у `receiving-items.ts`). Тепер `upsertReceivingDocumentItem`/`updateReceivingDocumentItemReceived` лише пишуть значення позиції й лог-подію (`receiving_document_item_events`), stock не чіпають. Уся сума `received` по позиціях додається на склад одноразово в `completeReceivingDocument` — це і є момент «оприходування» («саме оприходування на склад було саме після натискання кнопки Завершити»). Наслідок: `deleteReceivingDocument` тепер відкочує stock лише якщо `completedAt` уже стоїть (до завершення — нічого не було додано, відкочувати нічого); `deleteReceivingDocumentItem(s)` більше взагалі не чіпають stock (документ, доки редагований, завжди `!completedAt`, а мутації позицій і так заблоковані гардом після завершення — стара логіка відкату там стала мертвим/помилковим кодом і видалена).
**2. Гейт створення — прибраний, тип обирається у випадному меню.** Попередній прохід зробив «розумну» форму створення: документ автостворювався, щойно заповнені постачальник+відповідальна особа, а до того ліва частина (сканування) була заблюрена. Людина попросила прибрати цю механіку повністю («редагувати все можна одразу»), спершу запропонувавши замінити перемикач isPlanned на 2 радіокнопки прямо у формі — але коли я поставив уточнююче питання про сумісність із наявною машиною станів `awaiting_delivery`/«Прийняти на склад» (яка вимагає тип фіксованим від створення), людина сама відкинула цю ідею й запропонувала простіше: тип обирається у випадному меню одразу на кнопці «Додати надходження» (список), документ створюється відразу з фіксованим `isPlanned` і повністю редагованим — решта логіки (машина станів, «Прийняти на склад») лишається без змін. Постачальник/відповідальна особа заповнюються вже на сторінці документа звичайним автозбереженням (як і решта полів) — не обов'язкові для сканування, лише для «Завершити» (кнопка `disabled` з `title`-підказкою, поки їх нема).
Чому фіксую саме розвилку з питанням: пряме уточнення врятувало від зайвої роботи — вже почав був додавати радіокнопки в `PlannedReceivingInfoForm`, але оскільки основне рішення (де фіксується тип) людина змінила сама після одного точного питання, встиг відкотити мінімальний шматок коду, не всю фічу.
**3. `useUnsavedChangesGuard` — застосування прибрано з receiving.** Guard був потрібен лише для проміжного стану «форма створення, документа ще нема» — якого тепер не існує (документ створюється миттю на кліку в меню, без проміжної сторінки). Сам хук (`src/hooks/useUnsavedChangesGuard.ts`) лишений у коді — переюзабельний, може знадобитись для інших форм.
**4. Відповідальна особа — випадний список, не вільний текст.** Поки нема авторизації/таблиці користувачів тенанта, єдина опція — `DEV_USER.name` (`src/lib/constants/dev-user.ts`, той самий TODO(auth)-плейсхолдер, що вже використовує `products.ts` для `created_by`/`updated_by`). Реальний перелік користувачів — коли з'явиться авторизація.
**5. Склад — нередагований, якщо вже проставлений з контексту.** `WarehouseCard` (сторінка `/warehouse`) веде на список надходжень з `?warehouseId=`; список передає його в `ReceivingHeader`, який включає в `createReceivingDocumentAction`. Якщо `warehouseId` проставлений при створенні (чи обраний уручну пізніше — перше обрання так само фіксує), «Склад» у `PlannedReceivingInfoForm` показується звичайним текстом без `Select` — «я вже обрав склад, навіщо ще раз».

## `tenants`: RLS увімкнено без policy (deny-all), спричинено Supabase security linter
Supabase Dashboard показав security-попередження «RLS Disabled in Public» на `public.tenants` одразу після переїзду на hosted Postgres (`env.md`). Причина, чому це не було проблемою на локальному Docker: там немає публічного REST API над базою; на Supabase кожна таблиця схеми `public` за замовчуванням віддається назовні через PostgREST (Data API) ролям `anon`/`authenticated` (той самий механізм, яким користуються клієнти Supabase JS SDK) — і Postgres без `ENABLE ROW LEVEL SECURITY` не обмежує доступ узагалі, незалежно від того, чи застосунок сам колись користується цим API. `tenants` — єдина таблиця в схемі без RLS: це свідомий виняток із правила «tenant_id на кожній таблиці» (розділ 6 CLAUDE.md, задокументовано в `db.md` від самого початку), бо вона сама є довідником тенантів і `tenantIsolationPolicy` (звірка з `tenant_id`) до неї не застосовна. Перевірив усі інші 29 таблиць схеми (`grep enableRLS` по `src/server/db/schema/*.ts`) — решта вже мали `.enableRLS()`, `tenants` була єдиним пропуском.
Рішення: `.enableRLS()` без жодної `pgPolicy` — не «дозволити читати всім», а протилежне: Postgres із увімкненим RLS і без жодної policy забороняє доступ УСІМ non-owner ролям (fail-closed), включно з `app_user`, `anon`, `authenticated`. Безпечно для функціоналу — застосунок ніколи не читає `tenants` напряму через `app_user` (перевірено `grep`: лише FK-посилання `.references(() => tenants.id)` в інших таблицях, жодного `db.select().from(tenants)` у `src/server/data/*`), лише сідинг/міграції (роль-власник, обходить RLS за визначенням). Решта таблиць уже мали `tenantIsolationPolicy`, яка й без цього fail-closed для PostgREST-з'єднань: сесійна змінна `app.tenant_id` встановлюється лише в `withTenant()` (`src/server/db/client.ts`), у PostgREST-з'єднанні її нема — `current_setting(..., true)` повертає `NULL`, порівняння хибне, доступ забороняється. Міграція `0031_naive_stature.sql` — один рядок (`ALTER TABLE tenants ENABLE ROW LEVEL SECURITY`), застосована й перевірена (`pg_class.relrowsecurity = true`).
Додаткове зміцнення, не зроблене зараз (не просили, лише озвучено людині): Supabase Dashboard дозволяє взагалі прибрати `public` зі списку «Exposed schemas» (Settings → API → Data API) — тоді PostgREST не обслуговуватиме жодну таблицю `public` схеми незалежно від RLS, оскільки застосунок підключається напряму по Postgres-протоколу (не через Supabase Data API/JS SDK) і цей API взагалі не потрібен.

## Динамічні характеристики картки товару: три нові таблиці замість розширення `products`, повна заміна хардкоду
Наступний крок після «Закріплення характеристик»: картка товару читає той самий `characteristic_key`, що категорія (`category_characteristics`), і показує лише закріплене. Людина явно обрала «Повна заміна» (не додавання поруч із хардкодом) — коли зʼясувалось, що поточні поля Бренд/Колекція/Сезон/Посадка/Виробник/Матеріал/Тип тканини/Інструкція по догляду на картці товару були **повністю відірвані від довідників**, навіть тих, що вже реально в БД (Бренди/Колекції/Сезон/Посадка вже існували як `custom_characteristics`, картка товару їх просто не читала).
Три нові таблиці, не розширення `products`: (1) `product_characteristic_values` — той самий generic-принцип «вільний `characteristic_key`, без FK на value_id», що вже виправдав себе для категорій; (2) `product_material_composition` — окрема таблиця для «Тип тканини та матеріал», бо людина попросила особливу форму (тип тканини + розкладка «матеріал–%», не просто вибір значення) — генерична таблиця тут не підійшла б, склад має власну структуру (реальний FK на `materials`, не opaque id); (3) `product_characteristic_layout` — **тенант-рівнева**, не per-товар: людина захотіла drag&drop-розподіл характеристик по двох панелях картки (ProductInfoPanel/ProductMetaPanel) з порядком, що діє одразу для всіх товарів, поки я редагував лише один товар — розділив на окрему сутність замість додавання layout-полів у `product_characteristic_values`.
8 колонок `products` (`brand`/`collection`/`season_type`/`fit`/`country_of_origin`/`manufacturer`/`material`/`fabric_type`) видалено тим самим проходом (не залишено як мертві) — вони були точним дублюванням того, що замінюють нові таблиці, тримати обидва джерела означало б розбіжність без користі. `gender` лишився (немає відповідного довідника серед 9 джерел — не вигадував новий, узгоджено з людиною), `season`/`description` лишились без змін (поза системою характеристик).
Кольори/Постачальники свідомо виключені з динамічної секції (мають власний UI — SKU-конструктор, панель метаданих) — людина підтвердила «пропускати завжди», а не дублювати. Розміри/Заміри (`size-type:*`/`measurement-type:*`) теж виключені цього разу — вкладка «Розміри та заміри» ще на хардкоді, підключення туди лишається окремою майбутньою задачею, не робив мовчки «заодно».
Бренд/Колекція в хлібних крихтах (`ProductHeader`) резолвляться пошуком характеристики за відображуваним **лейблом** («Бренди»/«Колекції»), не `system_key` — на відміну від «Тегів» (де `system_key` навмисно вводили через ту саму крихкість). Свідомий компроміс: додавати `system_key` ще чотирьом характеристикам заради двох рядків тексту в хедері — понад те, що просили; перейменування характеристики людиною мовчки зламає лише напис у хлібних крихтах, не саму функціональність.
Чому фіксую: показовий приклад, коли вже наявний і перевірений патерн (`characteristic_key` без FK) свідомо переноситься на нову сутність один-в-один, а не винаходиться заново — і водночас приклад, коли частина нових вимог (розкладка складу, тенант-рівневий layout) навмисно НЕ форсується в той самий generic-патерн, а отримує власну, вужчу модель, бо мала іншу форму даних.

## Журнал подій товару: без номера поставки/замовлення, diff лише по прямих колонках `products`
Людина попросила лог подій товару з номером поставки (якщо подія — поставка) чи номером замовлення (якщо продаж). Перед реалізацією уточнив через `AskUserQuestion`, бо модулів «Постачання»/«Замовлення» в проєкті ще нема (`roadmap.md` — не почато): додавати `supply_number`/`order_number` зараз означало б вигадувати поля під сутності, яких не існує (порушення розділу 9.8 CLAUDE.md). Підтверджено — зараз лише `created`/`updated`, номери поставки/замовлення додати пізніше, коли з'являться самі модулі (нове `eventType` + nullable-поле номера в `product_activity_log`, схема вже готова під розширення без ламання наявних рядків).
Друге уточнення — рівень деталізації: людина обрала diff по кожному зміненому полю (не один узагальнений запис на збереження), попри те що автозбереження пише ВЕСЬ стан форми одним запитом щоразу. Реалізовано порівнянням рядка `products` ДО update із тим, що saveProduct от-от запише (`diffProductFields`) — лише прямі скалярні колонки (назва/статус/категорія/постачальник/ціни/розміри посилки тощо), НЕ значення динамічних характеристик/складу тканини/замірів/тегів (ті — junction-таблиці, id→лейбл резолвиться лише на клієнті, поза `saveProduct`) — свідомо вужчий обсяг, а не спроба задіфити геть усе одразу.
Третє — порядок полів нової вкладки «Технічні дані» (drag&drop): tenant-рівнева персистентність (нова таблиця `product_technical_layout`), той самий принцип, що вже є для порядку динамічних характеристик (`product_characteristic_layout`) — обрано свідомо, а не клієнтський стан, що забувся б при перезавантаженні.
Побічно виправлено давню прогалину: `products.created_by`/`updated_by` існували в схемі з самого початку, але ніде не заповнювались поза сідом-мокою (`saveProduct`/`createProduct` їх просто не чіпали) — тепер пишуться (`DEV_USER.name`), бо без цього поля «Створив»/«Останній редагував» (тепер видимі на новій вкладці) і сам актор журналу показували б порожнечу назавжди.

## Фото товару — тільки за кольором, таблицю `product_photos` видалено
Дві таблиці фото (`product_photos` — «фото моделі», `product_color_photos` — фото кольору) співіснували з моменту, коли фото кольору вводили окремим проходом. Людина сформулювала правило прямо: фото товару додається **тільки** в таблиці варіантів, під назвою кольору, і більше ніде — бо будь-яке фото товару завжди зображує конкретний колір. Отже «фото моделі» без кольору — сутність без сенсу, а дві таблиці для одного й того самого — гарантована розбіжність.
Обрано (варіант людини з трьох запропонованих) повне видалення, не «прибрати з UI, таблицю лишити»: міграція `0037` дропає таблицю, разом з нею пішли схема, data-шар, обидві Server Actions, API-роут `api/uploads/products/[id]`, поле `Product.photos`, мок і сідування. Явно попереджав, що вже завантажені «фото моделі» зникнуть назавжди — підтверджено.
Побічна залежність, яку довелось закрити тим самим проходом: мініатюра в списку `/products` (`listProducts`) читала саме `product_photos` — без переведення на `product_color_photos` (перше фото першого кольору за `position`) список лишився б без картинок. Тенант-фільтр і композитний індекс `(tenant_id, product_id, color, position)` покривають новий запит так само, як покривали старий.
`ProductPhotoGallery` натомість став переглядовим: показує всі фото кольорів однією сіткою з підписом кольору під кожним знімком (підпис — вимога людини, живе тільки в CRM, на вітрину не йде). Джерелом свідомо взято `skuMatrix.colors` (клієнтський стан конструктора), а не серверний проп — інакше нове фото не зʼявлялось би в галереї до перезавантаження сторінки.

## Вкладка «Основне»: порядок блоків = порядок заповнення, панелі без `h-full`
Людина описала дві різні проблеми однією фразою («все стає негарним і не вирівненим»): (1) технічну — картки в гріді з `h-full` розтягуються під найвищу сусідку, тож більше значень в одній панелі означає порожнечу в іншій; (2) змістову — характеристики, ціни й поля товару лежали впереміш в одній `ProductInfoPanel`, без логіки «спочатку те, від чого залежить решта».
Технічну закрито `items-start` на гріді + колонки як самостійні стеки карток (правило винесено в `ui-kit.md`, воно загальне, не про товар). Змістову — розрізанням на три блоки з порядком за залежностями: Основне (категорія першою — вона гейтить характеристики, кольори, розміри, заміри) → Характеристики → Варіанти SKU → Ціни (закупівельна перша, решта рахується від неї) → Деталі SKU → Фото.
Компонування обирала людина з трьох ескізів — обрано «дві колонки», не «смуги-кроки на всю ширину», попри те що смуги радикальніше розвʼязують проблему вирівнювання (широкий блок не має сусіда). Причина — щільність: смуги дають довгу сторінку зі скролом, що суперечить `design.md` («багато даних на екран»).
Дві дропзони тенант-layout-у характеристик (`info-panel`/`meta-panel`) лишились обидві — стали двома колонками всередині нового `ProductCharacteristicsPanel`. Альтернативу «одна дропзона» людина відхилила саме тому, що вона вимагала б злити наявний розклад (усі `meta` в кінець `info`) і частково втратити поточне розташування, накликане вручну.

## Перемикач «Для всіх розмірів однакова»: нова колонка `products.same_size_pricing`, не клієнтський стан
Людина уточнила мід-сесії (без окремого запиту, просто дописала до задачі): в блоці «Ціни та маржа» потрібен перемикач, і коли він увімкнений — `SKUDetail` не показує про ціни взагалі (не просто задизейблені поля, а відсутні рядки). Обрано персистентний `boolean` на `products` (`same_size_pricing`, `NOT NULL DEFAULT true`), а не локальний `useState` у компоненті — бо це бізнес-правило товару («цей товар продається за однією ціною незалежно від розміру»), яке має пережити перезавантаження сторінки й потрапляти в журнал подій товару (додано в `PRODUCT_ACTIVITY_FIELD_LABELS`, `product-activity-diff.ts`) так само, як решта цінових полів.
За замовчуванням `true` (типовий випадок — однакова ціна для всіх розмірів), тому наявні товари після міграції не показують override-поля в `SKUDetail`, поки хтось свідомо не вимкне перемикач.

## Штрихкод SKU: справжня персистентність + жорстка унікальність у БД, не лише UI-заглушка
При роботі над `SKUDetail` виявилось, що поле «Штрихкод (EAN)» ніколи насправді не зберігалось — локальний `useState` малював редагування, але жодного Server Action не викликав; сам компонент `sku` там і зовсім був мок-заглушкою (`defaultSelectedSku`), не реальним SKU з БД. Людина прямо зажадала: штрихкод — жорстка привʼязка «один ШК → один SKU», з перевіркою саме в БД (не лише в застосунку), бо майбутня прийомка товару працюватиме за принципом «скан ШК → знаходить SKU» — двозначність тут неприпустима.
Частковий `UNIQUE(tenant_id, barcode) WHERE barcode IS NOT NULL` на `product_skus` уже існував у схемі з першого проходу SKU-конструктора (для майбутнього використання), просто не був підключений до жодного реального шляху запису. Додано: `updateSkuBarcode` (data-шар, ловить `23505` і повертає дружнє повідомлення), `updateSkuBarcodeAction` (Server Action), і `SKUDetail` тепер викликає їх напряму замість фейкового локального стану. `activeSkuDetail` у `ProductGeneralTab` перестав бути суцільним моком — `id`/`barcode` тепер реальні поля вибраного SKU.

## Основне фото товару: одне з наявних, глобальне на товар (не на колір)
Людина захотіла можливість позначити одне з наявних фото як «головне» — воно рендериться помітно більшим у галереї. Питання, яке довелось вирішити: основне фото стосується товару в цілому чи окремого кольору? Обрано «товару в цілому» (не по кольору) — нова колонка `product_color_photos.is_main`, а не окрема таблиця/поле на рівні кольору, бо галерея показує фото всіх кольорів однією стрічкою, і зображення для вітрини одне на товар, незалежно від того, до якого кольору воно фізично прив'язане.
Частковий UNIQUE-індекс (не лише прикладна перевірка «скинути решту перед встановленням нового») — той самий принцип, що для штрихкоду вище: гарантія на рівні БД, не лише дисципліни коду.

## Перемикач «Для всіх розмірів однакова», основне фото, жорсткий ШК — три незалежні db-рівневі гарантії в одній сесії правок UI
Сесія почалась як суто верстка (розкладка вкладки «Основне»), але дорогою виявила три місця, де видима поведінка вже малювалась в UI, а реального збереження в БД не було (перемикач цін, штрихкод SKU) або взагалі не існувало (основне фото). У кожному випадку рішення — не локальний `useState`-стан, а нова колонка з обмеженням цілісності (звичайний `NOT NULL DEFAULT`, частковий `UNIQUE`), бо йдеться про бізнес-правила товару, які мають пережити перезавантаження сторінки й (для ШК) гарантувати однозначність незалежно від того, хто й звідки редагує.

## Фото товару: без ліміту кількості, перегляд/видалення лише в галереї, не в таблиці
Людина прибрала ліміт `MAX_COLOR_PHOTOS = 3` повністю — і в UI (перевірка `photos.length < MAX_COLOR_PHOTOS` у `ColorPhotosControl`), і в Server Action (`uploadColorPhotoAction` більше не рахує наявні фото перед вставкою). Причина не пояснювалась окремо, але узгоджується з тим, що галерея (`ProductPhotoGallery`) тепер повноцінне місце перегляду з лайтбоксом — штучне обмеження втратило сенс.
Заразом прибрано прев'ю мініатюр і кошик видалення з `ColorPhotosControl` (таблиця варіантів) — людина прямо сказала «у таблиці фото показувати вже не потрібно». Видалення фото не зникло, а переїхало в `ProductPhotoGallery` (кошик на наведенні, і на великому фото, і на мініатюрах) — `useProductSkuMatrix.deletePhoto` сам шукає, якому кольору належить фото (галерея знає лише пласкій список, не `colorId`), таблиця лишається єдиним місцем **завантаження**, галерея — єдиним місцем **перегляду й видалення**.

## Основне фото — object-contain, не аспект-квадрат: показує фото в реальній пропорції
Перша версія великого фото використовувала `aspect-square`+`object-cover` (як і мініатюри) — людина прямо поправила: велике фото має «вміщатися в тій пропорції, в якій завантажено», тобто без кадрування. Замінено на гнучкий блок (`flex-1`, без фіксованого аспекту) з `object-contain` — зображення завжди ціле, портретне/альбомне/квадратне фото не обрізається, лише центрується в доступному просторі (можливі поля зверху/знизу чи з боків, це очікувано для object-contain, не баг).

## Гочта: h-full не спрацьовував через DevBlockLabel — батько без явної висоти ламає відсоткову
Три панелі ряду 1 (Фото/Основне/Характеристики) не вирівнювались по висоті навіть після прибрання `items-start` і додавання `h-full` на картки — причина не в гріді, а в `DevBlockLabel` (`DEV_BLOCK_LABELS.products = true` в цьому середовищі, отже компонент активний): його обгортковий `<div>` не мав явної висоти, і CSS-правило «`height: %` ігнорується, якщо в батька `height: auto`» гасило `h-full` картки, що лежить усередині. Виправлено додаванням `h-full` до самого `DevBlockLabel` (спільний dev-компонент, `ui-kit.md`) — відтоді ланцюжок стретчнутий грід → обгортка → `DevBlockLabel` → картка передає визначену висоту без розривів.
Чому фіксую: непомітна гочта, яка вдарить знову, якщо колись знадобиться ще один шар-обгортка (не обов'язково dev-інструмент) між грід-коміркою і панеллю, що має `h-full`.

## Склади: ручна 3-колонкова структура адресного зберігання замінила bulk-генератор
Людина, дивлячись на живий склад, попросила інший робочий процес замість крос-добуткового генератора (вулиці×стелажі×комірки одним числом кожен, `WarehouseBinGenerationWizard` з dry-run): 3 колонки, кожен рівень (вулиця/стелаж/комірка) створюється окремо («+» — одне значення, поле кількості — партія), з видаленням на кожному рівні (каскадно) і реальним друком PDF-етикеток. Погоджено замінити старий генератор повністю, не тримати обидва способи — менше плутанини, два шляхи створення тих самих комірок були б ризиком розбіжності.
Модель БД перейшла з плаского `warehouse_bin_locations` (рядок = готова комірка з усіма трьома рівнями одразу) на 3 таблиці батько→нащадок (`warehouse_bin_streets`/`racks`/`cells`) — ручне створення вулиці "самої по собі", без стелажів/комірок, вимагає окремої сутності для кожного рівня, не лише фінальних комірок.

## Нові залежності bwip-js + pdf-lib: справжній Code128 і PDF для друку етикеток
"Реальний скановий штрихкод" і "формується PDF" — тверді вимоги людини для друку етикеток комірок, а не косметика. Погоджено (`AskUserQuestion`, правило 9.9 CLAUDE.md) додати `bwip-js` (рендер Code128 у PNG на сервері, без DOM/canvas-залежностей — підходить і для попереднього перегляду, і для вставки в PDF) і `pdf-lib` (побудова PDF з точною міліметровою розміткою, чистий JS без нативних залежностей).
Заразом прибрано чекбокси «Автоматично генерувати штрихкоди»/«Створити QR-коди» і фейковий макет-компонент `WarehouseBinLabelPreview` (детермінований візуальний плейсхолдер, не справжня символіка) — штрихкод тепер завжди справжній і обов'язковий (потрібен для друку/сканування), QR не просили.

## Склади: "Структура адрес" злита в "Структура комірок", усе автозберігається
Третій прохід над «Адресним зберіганням» — людина прибрала окрему картку конфігурації (назви/формати/роздільник з явним «Зберегти») і перенесла її функціонал прямо в колонки `WarehouseBinExplorer`: назва рівня редагується інлайн (перегляд+олівчик), формат живе лише в блоці масового створення й запам'ятовується там же, роздільник зафіксовано на пробілі (не налаштування). Причина попереднього explicit-save винятку («перед потенційно масовою генерацією») зникла разом зі старим bulk-генератором (другий прохід) — кожна дія тепер стосується одного явно вказаного вузла чи партії, тож автозбереження одразу (типове правило conventions.md) знову доречне, окремий виняток більше не потрібен.
Заразом прибрано перемикач «Використовувати адресне зберігання» й чекбокс «Дозволити повторний друк етикеток» із вкладки — перший дублював перемикач на вкладці «Основне» (лишився тільки там), другий ніде не впливав на поведінку (зберігався, але не читався жодним кодом).

## Перевізники: власний модуль-абстракція (interface + factory + provider), без SDK
Пряма вказівка людини (2026-08-06) — повністю автономний `src/server/carriers/` (`carrier.interface.ts`+`carrier.factory.ts`+`novaposhta/{client,provider,endpoints,types,errors,mapper}.ts`), без жодної npm-залежності від Нової пошти чи від `github.com/shopanaio/carrier-api` (використано лише як довідник назв методів під час аналізу, разом з кількома незалежними типізованими сторонніми клієнтами — `docs/carriers/novaposhta/`). Раніше робочий код жив пласко в `server/integrations/nova-poshta.ts` — переїхав у `NovaPoshtaProvider` без зміни поведінки (той самий живий UI `settings-delivery.md` перевірено після переїзду, консольних помилок нема).
Чому: людина явно планує майбутнє — інші перевізники (Укрпошта/Meest/Rozetka) і ШІ в чаті на найвищому тарифі, що виконуватиме операції на кшталт «покажи, де моя посилка» через той самий універсальний інтерфейс (`calculate`/`createShipment`/`track`/`createReturn`/`redirectShipment`/`getCities` тощо). CRM звертається лише до `CarrierProvider`, ніколи до `modelName`/`calledMethod` Нової пошти напряму — новий перевізник означає новий провайдер під тим самим інтерфейсом, без правок бізнес-логіки. Методи без реальної інтеграції (не Нова пошта) чи ще не реалізовані (створення ЕН, трекінг, повернення, переадресація, друк — реальний побічний ефект, наосліп не тестували) кидають контрольовані `CarrierNotSupportedError`/`CarrierNotImplementedError`, не крашать систему.

## PDF-етикетки: шрифт Inter вбудовано напряму (файл), не окремим npm-пакетом
Друк PDF падав на будь-якій кириличній назві (`WinAnsi cannot encode`) — стандартні шрифти pdf-lib не мають кирилиці. Замість встановлення пакета на кшталт `typeface-inter` (15МБ, усі ваги й вирізки Inter) чи `@fontsource/inter` (лише розбиті по скриптах woff2 — окремо кирилиця без латиниці/цифр у файлі, не підійшло б для змішаного рядка "201 А 05"), витягнуто один потрібний файл (`Inter-Regular.woff2`, ~168КБ, той самий шрифт, що й у вебі, повний гарнітурний набір з кирилицею) і покладено просто як актив у `src/server/warehouse/fonts/` — обраний варіант зважує рівно стільки, скільки треба, без зайвої залежності в `package.json` заради одного файлу. `@pdf-lib/fontkit` — реальна нова залежність (обов'язковий супутник pdf-lib для вбудовування довільних шрифтів, не окремий вибір із альтернативами).
