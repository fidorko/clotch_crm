# Decisions

## Мітки компонентів у dev-режимі
Блоки/секції сторінки обгортаються `DevBlockLabel`, показ керується прапорцем на модуль (`lib/dev/dev-flags.ts`), вимикається разом зі зміною статусу UI на `готово`.
Чому: людина звіряє UI по скріншотах — назва компонента на екрані замість опису словами економить токени й виключає плутанину «яка це секція».

## SEO: розділення CRM і публічних сторінок
CRM-екрани (за авторизацією) — `noindex, nofollow` за замовчуванням через `metadata` розділового layout. Публічні сторінки (лендинг) отримають повне SEO окремо, коли з'являться.
Чому: мультитенантна CRM — індексація сторінок з чужими бізнес-даними є витоком даних (розділ 6 CLAUDE.md), а не просто зайвим трафіком.

## Завантаження фото товару: локальний прев'ю до підключення БД
`ProductPhotoGallery` показує вибране фото одразу (`URL.createObjectURL`), але нічого не зберігає — типи `ProductPhoto {id, url, alt}` не змінились, тож коли з'явиться бекенд, зміниться лише джерело `url` (blob → реальний), верстка й рендер-логіка лишаються тими самими.
Чому: дає реальну взаємодію зараз без зайвої роботи, яку доведеться переробляти — реальне збереження вимагає файлового сховища й таблиці в БД (ще в беклозі).

## БД: Drizzle + postgres.js, не pg
`drizzle-orm/postgres-js` + пакет `postgres` замість `node-postgres` (`pg`).
Чому: перше-класна підтримка в Drizzle, нативний TS API без окремих `@types/pg`, простіший singleton-патерн для Next.js dev-режиму (HMR). Рішення низького ризику — легко зворотне за потреби.

## БД: pricing — плоскі numeric-колонки, не jsonb
14 цінових колонок у `products` (`purchase_price`, `old_price` + 4 канали × `mode`/`amount`/`percent`) замість jsonb чи окремої EAV-таблиці.
Чому: набір полів фіксований і не тенант-конфігурований (не EAV-випадок); ціна — очікуване поле для `WHERE`/`ORDER BY` на майбутньому списку товарів, а індексувати/планувати запити по значенню всередині jsonb суттєво гірше за звичайний `numeric`. Переглянути, якщо з'являться динамічні/per-тенант цінові рівні (див. `db.md`).

## БД: RLS увімкнено одразу в першій міграції
Кожна прикладна таблиця має `ENABLE ROW LEVEL SECURITY` + політику `tenant_isolation` з першого дня, а не як окрема задача «колись пізніше». Застосунок підключається non-owner роллю `app_user` (не власником, яким котяться міграції) — інакше RLS не перевіряється жодним запитом і існує лише на папері.
Чому: ретрофіт RLS на таблиці з даними — ризикованіша операція (треба перевірити, що жоден існуючий запит не покладався на обхід RLS), ніж додати одразу; RLS не залежить від наявності авторизації — джерело `tenant_id` для сесійної змінної однаково тимчасове (dev-константа), незалежно від того, коли підключати RLS.

## БД: категорія/колекція — прибрано дублювання з TS-типу
До підключення БД `Product` мав одночасно `category`, `info.category` (повний шлях) і `breadcrumb` (масив), а `collection` дублювався з `info.collection`. Спрощено: `category` (коротко) + `categoryPath` (повний шлях, БД: `category_path`), одна колонка `collection`, `breadcrumb` більше не зберігається — рахується на рендері (`ProductHeader`) з `category` + `name`.
Чому: зберігати дублікати означало б синхронізувати кілька джерел істини при кожній зміні назви/категорії товару; дублювання в типі не мало причини — просто накопичилось по ходу верстки.

## БД: автобутстрап через `predev`, не git-хук
`npm run dev` сам піднімає Docker (`--wait`) і накочує міграції/роль (`predev` у `package.json`) — замість git-хука на `post-merge`/`git pull`.
Чому: хуки в `.git/hooks` не передаються через `git pull`/`clone` — довелось би окремо налаштовувати на кожній машині, та сама зайва дія, якої хотіли уникнути. Прив'язувати підняття Docker і зміни в БД до звичайної, зазвичай пасивної команди `git pull` — несподівана поведінка. `npm run dev` — команда, яку й так вводять свідомо перед початком роботи.

## Зображення категорій: реальне файлове сховище, на відміну від фото товару
На пряме прохання підключено зараз (не blob-прев'ю, як досі в `ProductPhotoGallery`) — диск поза `public/`/`src/` (`storage/uploads/<tenantId>/categories/`), роздача через власний route handler, а не напряму. Деталі — `db.md`.
Чому: свідомий виняток із загального принципу «відкладати реальне зберігання, поки не попросять» (`decisions.md` вище, фото товару) — тут прямо попросили зараз. Product-фото цим не зачіпаються і лишаються blob-only, це не автоматичне поширення рішення на весь проєкт.

## Зображення категорій: `tenantId` для роздачі — з сесії, не з URL
Route handler `api/uploads/categories/[filename]` бере `tenantId` через `getDevTenantId()` на сервері; `filename` у URL — опаковий UUID без вкладеного `tenant_id`. Ізоляція тенантів для файлів досягається тим, що чужий тенант шукає файл у *своїй* теці на диску (де його нема), а не перевіркою «чи цей filename належить цьому tenant_id» (такої перевірки й не потрібно).
Чому: пряма аналогія з правилом 3 розділу 6 CLAUDE.md для БД (`tenant_id` тільки з сервера, ніколи з клієнта) — застосована і до файлової системи, щоб той самий принцип не довелося винаходити наново, коли з'явиться реальна авторизація.

## Видалення категорії з дітьми: блокує сама БД (FK RESTRICT), не лише код
`categories.parent_id` — `ON DELETE RESTRICT`. `deleteCategory` ловить `error.cause.code === '23503'` (Drizzle обгортає сиру помилку `postgres.js` — код лежить у `.cause`, не на самій помилці) і повертає дружній текст.
Чому: обмеження на рівні схеми — надійніше за app-level перевірку «чи є діти» перед видаленням (немає вікна для гонки запитів, і захищає навіть якщо колись з'явиться інший шлях запису до таблиці).

## products.category_id: SET NULL, не RESTRICT (на відміну від categories.parent_id)
`products.category_id` (FK на `categories.id`) — `ON DELETE SET NULL`. Видалення категорії просто знімає прив'язку в товарів, не блокується.
Чому: інша семантика, ніж `categories.parent_id` (там `RESTRICT` — не можна видалити категорію з дітьми). Тут блокувати видалення категорії через те, що на неї посилаються товари, було б надто суворо й несподівано для власника магазину — товар просто стає без категорії, а не «застряглою» причиною неможливості прибрати застарілу категорію.

## Редагування полів-довідників у ProductInfoPanel: олівчик, а не завжди відкритий список
Категорія/Колекція/Стать/Сезон/Посадка/Виробник/Матеріал/Тип тканини — тепер «текст + олівчик → відкрити список» (новий `EditableSelectRow`), а не завжди видимий `Select`, як було. Категорія в режимі перегляду показує повну ієрархію («Одяг / Джинси»), не тільки кінцеву назву.
Чому: пряме прохання — уніфікувати з уже наявним патерном `PurchasePriceRow` (перегляд/редагування явно розділені), а не тримати два різні візуальні стилі редагування в одній панелі.

## Хлібні крихти — з реальної категорії (categoryId), не з текстового поля
`ProductHeader` рахує крихти через `getCategoryPath(categories, product.categoryId)`, а не `product.category` (застаріле текстове поле, не оновлюється автоматично при виборі категорії).
Чому: після підключення `categoryId` текстове поле `category` стало потенційно застарілим — крихти мають показувати те, що людина реально обрала, а не historical/дефолтний текст із моку/сіду.

## HeaderActions: DEV_USER — реальні ім'я/email людини, не generic-заглушка
`lib/constants/dev-user.ts` (`{ name: "Дмитро", email: "fidorko.dv@gmail.com" }`) — показуються в `UserMenu` (аватар-чіп у шапці), поки немає авторизації. Перед тим як писати — прямо спитав людину, чи вона усвідомлює, що реальні ім'я й особиста пошта потраплять у git-історію репозиторію (`fidorko/clotch_crm`, GitHub) назавжди, навіть після заміни значення. Людина підтвердила — хотіла точно так, як на її ж скріні-зразку.
Чому фіксую окремо: це свідомий виняток із типового «не вигадуй/не хардкодь особисті дані» — не мовчазне рішення асистента, а прямий, підтверджений вибір людини з озвученим ризиком. Якщо колись репозиторій стане публічним або зміниться власник — варто прибрати цей коміт із git-історії (`git filter-repo`/BFG), не просто замінити значення в HEAD.

## Постачальники: месенджери/соцмережі — справжні бренд-іконки через `react-icons`
`lib/constants/supplier-options.ts` — Telegram/Viber/WhatsApp/Facebook/Instagram/TikTok/Threads показують фірмову іконку бренду (`react-icons/fa6`, набір `Fa*`) у кружечку брендового кольору, не текстовий код.
Чому: `lucide-react` (єдина іконкова бібліотека проєкту) не має жодної брендової іконки — спершу зробив тимчасовий компроміс (кружечок з 2-літерним кодом замість лого, без нової залежності), але людина прямо попросила саме «фірмові» іконки. Погодив із людиною через питання (`AskUserQuestion`) — обрала `react-icons` замість самописних inline SVG (правило 9.9 CLAUDE.md дотримано: нову залежність не додавав без явної згоди).

## Валюти: окрема таблиця, не reference_items; курси НБУ — по кліку, не за розкладом
`currencies` — власна таблиця (код/символ/позиція/знаки після коми/курс/автооновлення), не спільний `reference_items` (той — лише «просто назва»). «Автооновлення» за замовчуванням увімкнено (`auto_update = true`), джерело курсу — публічний API НБУ (`src/server/integrations/nbu.ts`), але реального планувальника (cron) у проєкті нема — обидва виклики (одинична й пакетна кнопка «Оновити курс(и)») спрацьовують лише по кліку користувача.
Чому: додавати вигаданий/непрацюючий "автоматичний" механізм було б нечесно (виглядало б як робоче автооновлення, а насправді нічого не оновлювало б само); яку платформу деплою й спосіб планування (Vercel Cron, зовнішній тригер на API-роут тощо) використовувати для справжнього розкладу — рішення, яке варто узгодити з людиною окремо, коли з'явиться деплой, а не вигадувати мовчки зараз.

## Довідники «Характеристики товару»: дві генеричні таблиці, не enum і не нова колонка на кожну
Людина сумнівалась, чи можна дати власнику магазину самому створювати нові прості довідники («Тип комірця» → «Суцільнокрійний, Крильце, Ліхтарик») без втручання розробника — чи не знадобиться нова колонка/таблиця в БД на кожну таку характеристику. Відповідь: ні, не знадобиться. `custom_characteristics` (сама характеристика) + `custom_characteristic_values` (її значення, FK з `ON DELETE CASCADE`) — одна пара таблиць покриває довільну кількість довільно названих характеристик, без DDL при кожному створенні.
Чому не розширили натомість `reference_items.kind` (уже наявний спільний довідник для 8 «просто назва» пунктів): `kind` — фіксований pg-enum, значення задаються в коді розробником (`REFERENCE_ITEM_KINDS`). Дозволити людині вводити довільну назву характеристики в попапі означало б `ALTER TYPE ... ADD VALUE` з боку застосунку на кожен новий ввід — DDL, ініційований користувачем через звичайну форму, і Postgres до того ж не вміє `DROP VALUE` (уже наступали на це, коли `currencies` вийшов з `reference_items` — `db.md`). Дві прості таблиці — стандартний, передбачуваний шлях, той самий, що вже використаний для `tags`/`colors`, тільки з додатковим рівнем «характеристика → значення».

## Теги: перенесено з окремої таблиці tags у custom_characteristics — свідомий ризик, підтверджений людиною
Раніше `tags`/`product_tags.tag_id` — окрема таблиця з реальним зв'язком товар↔тег. За прямою вказівкою («Такі прості довідники як... Теги... також перетвори в користувацькі») перенесено в `custom_characteristics` (рядок з `system_key="tags"`) + `custom_characteristic_values`, `product_tags.tag_id` замінено на `characteristic_value_id`. Перед реалізацією прямо спитав людину: це означає переробку `syncProductTags`/`product_tags` і ризик зламати вже робоче присвоєння тегів товарам — людина підтвердила («Справді перенести в custom_characteristics»), усвідомлюючи ризик.
Наслідок, який людина також свідомо прийняла: оскільки «Теги» тепер звичайна `custom_characteristics`-характеристика, її можна видалити через кнопку-кошик у попапі, як будь-яку іншу — видалення каскадно прибирає ВСІ теги з УСІХ товарів тенанта одразу (не лише один тег). Захисту від цього навмисно не додано — послідовно з рішенням «Теги — така сама користувацька характеристика, як решта».
Технічний захист від тихої втрати даних, який усе ж додано: `updateCustomCharacteristic` переносить значення діфом (не `delete-then-insert` усього списку) — інакше кожне збереження попапу «Теги» (навіть без реальної зміни значень) переприсвоювало б `id` усім значенням і мовчки відв'язувало теги від товарів через `ON DELETE CASCADE`. Дворазова міграція (додати нове поруч → перенести дані одноразовим скриптом → прибрати старе) виконана без втрати наявних dev-даних (4 теги, 4 зв'язки товар↔тег — перевірено до і після).

## tenantId: dev-константа до авторизації, але типізований параметр з першого дня
`src/server/tenant/get-tenant-id.ts` (`DEV_TENANT_ID` з `.env`) — до появи авторизації. Сигнатури data-access шару (`src/server/data/*`) вже приймають `tenantId` як обов'язковий типізований параметр незалежно від джерела.
Чому: дозволяє підключити БД і почати зберігати реальні дані вже зараз, а перехід на сесії пізніше буде заміною одного джерела значення в місцях виклику `getDevTenantId()`, не переробкою архітектури data-access шару.
*(Заголовок цього запису раніше помилково дублював заголовок «Довідники «Характеристики товару»...» вище — виправлено, вміст запису не змінювався.)*

## Перемикачі довідника (CRM/вітрина/фільтри) для не-custom_characteristics: окрема генерична таблиця, не розширення colors/reference_items
За наступним зауваженням («ті 3 перемикачі повинні бути на всіх довідниках характеристик товару») перемикачі знадобились і для довідників групи «Характеристики товару», які не є `custom_characteristics` — спершу «Кольорів»/«Тип тканини та матеріал» (список рядків, а не один запис «на весь довідник»), а за наступним уточненням людини («не на всіх» → «Розміри та заміри», «ще інструкції») — і для «Інструкція по догляду»/«Розміри та заміри», які взагалі ще без власної БД-таблиці зі списком значень. Замість трьох нових boolean-колонок у `colors`/`reference_items` (і вигаданих колонок у таблиці, якої ще нема для двох останніх) — нова генерична таблиця `reference_dictionary_flags` (`tenant_id`, `dictionary_key`, 3 boolean, PK з обох перших колонок), ключована просто рядком, не залежна від того, чи є в довідника реальний список значень.
Чому: колонки в `colors`/`reference_items` довелось би дублювати на кожен рядок довідника (кожен колір мав би однакове значення прапорця — зайва денормалізація), а сенс прапорця — «на весь довідник», не на окремий колір/тканину; для «Інструкції по догляду»/«Розмірів та замірів» колонок у власній таблиці взагалі ще нема, куди їх додати. Окрема таблиця з ключем `dictionary_key` — той самий підхід, що вже виправдав себе для `custom_characteristics`/`custom_characteristic_values` (generic, а не колонка-на-кожен-випадок), масштабується на будь-який довідник, включно з тим, що ще не має власної таблиці, просто додаванням ключа.

## «Кольори» перенесено з окремої сторінки в попап; курсор — явний `cursor-pointer` на всіх клікабельних плитках
За прямою вказівкою: (1) `/settings/references/colors` (окрема сторінка) видалена — «Кольори» тепер плитка+попап (`ColorsTile`/`ColorsFormDialog`), як і решта довідників групи «Характеристики товару» (той самий `ColorsList` без змін усередині діалогу); (2) усі клікабельні елементи плиток «Довідники» отримали явний клас `cursor-pointer`.
Чому явний клас, а не якийсь глобальний фікс: у Tailwind v4 preflight не додає `cursor: pointer` нативним `<button>` за замовчуванням (на відміну від `<a>`) — саме тому частина плиток (посилання-`Link` на сторінки довідників) показувала «руку» при наведенні, а частина (кнопки-тригери попапів: кольори, користувацькі характеристики) — ні; людина помітила цю неоднорідність візуально. Правильний загальний фікс (перевизначити `button { cursor: pointer }` глобально в CSS-reset) не чіпали — точковий `cursor-pointer` на конкретних інтерактивних елементах безпечніший і не змінює курсор на кнопках, де це небажано (наприклад, `disabled`).

## «Тип тканини та матеріал»: окремі реальні таблиці, не розширення `reference_items`
За зразком-скріном людини («зроби такою») довідник виявився суттєво багатшим за «просто назва» (склад, можливі матеріали, сезон/розтяжність, зображення схеми, догляд) — спитав людину прямо, чи будувати окремі таблиці в БД замість поточного спільного `reference_items`; підтверджено (рекомендований варіант). Нові таблиці — `fabric_types` (сам тип) + `materials` (окремий повноцінний CRUD-довідник, не лише вкладені значення) + 4 junction-таблиці (склад/можливі матеріали/сезони/догляд, `db.md`).
Чому не розширили `reference_items.kind`: той довідник — навмисно лише «одна назва на рядок» (`db.md`), тут же потрібні структуровані зв'язки (матеріал+відсоток, багато-до-багатьох із чекбоксами) — jsonb чи розширення `reference_items` довелося б обходити прикладною логікою замість покладатись на FK/UNIQUE на рівні БД.

## «Категорії товарів» на типі тканини — свідомо не робили, за прямою вказівкою
Зразок-скрін мав чекбокси прив'язки типу тканини до категорій товару (Худі/Світшоти/Штани/Костюми/Футболки). Перед реалізацією спитав людину: прив'язати до реальної таблиці `categories`, чи окремий незалежний список — людина відповіла прямо «категорії товарів туди не додавай». Розділ у `fabric_types` не створено взагалі (ні FK на `categories`, ні окремої таблиці); поле `recommended_use` лишилось вільним текстом («Худі, світшоти, штани») замість чекбоксів.
Чому фіксую окремо: це найпомітніше явне відхилення від скріна-зразка в цьому раунді — щоб при звірці (розділ 10 CLAUDE.md) не виглядало як недогляд, а не свідомий вибір людини.

## «Рекомендації по догляду» на типі тканини — реальний тенант-керований довідник, не хардкод-список
Спочатку планував фіксований («захардкоджений») набір пунктів догляду (як і сам скрін мовчки натякав — просто список іконок). Людина уточнила окремим повідомленням просто в процесі реалізації: «...потрібно зробити ще й деякі значення інструкцій для догляду в БД з іконками, щоб потім на сторінці матеріалів обирати з існуючих» — тобто самі інструкції мають бути реальними тенант-керованими записами (назва+іконка), а фіксованим лишається лише *набір іконок-кандидатів* для пікера при створенні запису, не самі інструкції.
Чому важливо розрізняти: перше трактування («фіксований набір іконок догляду») з попереднього раунду питань і друге уточнення на перший погляд суперечать одне одному, але насправді сумісні — «фіксований набір іконок» стосується лише палітри іконок для вибору, а не самих написів/значень, які лишились повністю в БД (`care_instructions`, `db.md`). Дало змогу заразом не плодити другий незалежний механізм поруч із вже наявною порожньою заглушкою-плиткою «Інструкція по догляду» — хоч вони й лишились не об'єднаними (`modules/settings.md`, «Відкрито»).

## Сід «Матеріали» з категоріями: `onConflictDoUpdate`, не типовий `onConflictDoNothing`
Перед запуском `db:seed` для 55 матеріалів людини перевірив БД напряму — там уже була «Бавовна» (`color = '#CCCCCC'`), створена людиною вручну через UI під час попереднього ручного тестування, і реально прив'язана до одного типу тканини (1 запис у складі, 1 — у можливих матеріалах). Типовий для сідів проєкту `onConflictDoNothing` (як у `colors`/`currencies`/`brands`) лишив би цей рядок без `category` назавжди, бо конфлікт на `UNIQUE(tenant_id, name)` просто пропустив би вставку. Замінив на `onConflictDoUpdate`, що на конфлікті оновлює лише `category` — `color`/`position` наявного рядка не чіпає, реальний зв'язок з типом тканини не порушено.
Чому фіксую окремо: єдиний сід у проєкті з такою поведінкою (решта — суворо `onConflictDoNothing`), і причина не очевидна з коду без цього контексту — наступного разу, додаючи новий сід поверх довідника, куди людина вже могла щось вписати вручну через UI, варто спершу перевірити БД, а не просто копіювати `onConflictDoNothing` за замовчуванням.

## «Тип тканини»: без % складу й без прив'язки догляду — лише «Можливі матеріали»
Після побудови повної картки типу тканини (склад з %, прив'язаний догляд, зображення схеми) людина усвідомила помилку моделювання й попросила подумати, чи права вона: «тип тканини» (Футер, Кулір, Джерсі...) — це назва структури плетіння/переплетення, а не рецепт складу. Та сама структура в різних партіях постачальника чи різних товарах реально має різний % волокон — прив'язка фіксованого складу до довідника типу тканини видавала б одну випадкову партію за універсальну істину, і на кожному товарі однаково довелося б вводити реальний склад вручну. Те саме стосується догляду: реальні символи догляду на бирці залежать від фактичного складу конкретного виробу, а не від назви структури плетіння — раз склад не фіксований на рівні типу тканини, і догляд там фіксувати не можна.
Погодився з людиною й прибрав з `fabric_types`: `fabric_type_composition` (%), прив'язку `fabric_type_care_instructions`, і заразом (з того самого редизайну) `fabric_type_seasons` («Сезон не потрібен взагалі», окреме зауваження) та зображення схеми/нотатки (замінені трьома структурними полями — Лицьова/Тильна сторона, Тактильні відчуття). Лишилось тільки `fabric_type_possible_materials` — необов'язковий перелік «що типово зустрічається в цій структурі», без %, без твердження факту. Точний склад і догляд конкретного товару — майбутня властивість картки товару, не довідника (`db.md`).
Довідник `care_instructions` (назва+іконка), уже збудований і засіяний одним записом, **не видалено** — за прямою вказівкою людини лишений у коді про запас, без споживача в UI, для тієї майбутньої задачі.

## Пікер «Можливі матеріали»: груповий мультиселект-комбобокс з інлайн-створенням
Коли % склад прибрали, єдиним пікером матеріалів, що лишився, стала «Можливі матеріали» — раніше always-visible чекбокс-грід усіх матеріалів (незручно вже при 55 записах). Переробив на `Combobox` (`@base-ui/react/combobox`, `ui/combobox.tsx`) — пошук по вводу, групування за `materials.category` (`Combobox.Group`/`Combobox.GroupLabel`/`Combobox.Collection`, додані до спільної обгортки вперше — `ui-kit.md`), інлайн-створення нового матеріалу через синтетичний `value` (`"__create__"`), перехоплений в `onValueChange` до звичайного шляху вибору.
Чому саме так: людина явно описала бажаний UX («зверху пустий інпут — починаю писати, починає шукати; можна додати прям звідти новий матеріал»), і оскільки категорії матеріалів (`materials.category`) вже існували в БД (попередній раунд — сід 55 матеріалів), природно було одразу застосувати групування, а не лишати плоский список.

## «Тип тканини та матеріал»: без окремої сторінки — усе попапами з плитки
Одразу після побудови сторінки з двома вкладками людина уточнила: «попап залишаємо, а саму сторінку... можна видалити і одразу відкривати попап для створення та редагування». Прибрано `/settings/references/fabric-materials` цілком (разом з `FabricMaterialsWorkspace`/`FabricTypesTab`/`FabricTypesList`/`FabricTypeDetailPanel`) — плитка «Тип тканини та матеріал» у гріді «Довідники» тепер показує наявні типи чіпами (`FabricTypesTile`), кожен чіп — окремий тригер `FabricTypeFormDialog` у режимі edit; «+Додати» — той самий попап у режимі create. Питав людину прямо, де тоді бачити/обирати існуючі типи без сторінки — відповідь «Чіпи типів прямо на плитці» підтвердила цей напрям.
Видалення типу тканини переїхало в сам попап (кнопка в футері `FabricTypeFormDialog`, видима лише в режимі edit) — раніше жило в `FabricTypeDetailPanel`, якого більше нема. Довідник «Матеріали» (CRUD, колишня вкладка `MaterialsTab`) з тієї самої причини переїхав усередину `FabricTypeFormDialog` як згортана секція «Керувати довідником матеріалів» (перейменовано на `MaterialsManager`) — за прямою відповіддю людини на питання «де його місце» («усередині того ж попапу типу тканини»).
Чому не лишили окрему сторінку взагалі без вкладок: людина явно попросила прибрати сторінку як таку, не спростити її — весь принцип «Довідники» вже й так керується попапами прямо з плиток (`ColorsTile`/`CustomCharacteristicTile`), і «Тип тканини та матеріал» тепер узгоджений з цим самим патерном, а не є винятком з окремим маршрутом.

## «Можливі матеріали»: за замовчуванням усі, плюс масові дії
За прямою вказівкою: у новому типі тканини `possibleMaterialIds` ініціалізується повним списком наявних матеріалів (не порожнім) — власник магазину звужує список сам, а не збирає його з нуля. Додано «Обрати всі»/«Зняти всі» в `FabricTypePossibleMaterialsField` для швидкого масового керування (актуально вже при 55 матеріалах у довіднику). При редагуванні наявного типу — як і раніше, використовується збережений вибір, не перезаписується на «всі» повторно.
